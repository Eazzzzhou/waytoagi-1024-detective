# D1 统一评估标准

版本：v0.1（阶段 1）· 2026-10-24 · 负责人：乙

## 0. 范围与原则

本文件用于评估 D1 的人工参考判断、系统结果和两者对照。它不实现搜索或核查算法，也不替代丙的独立复核。

三个评估对象必须分开：

| 对象 | 评估什么 | 不能做什么 |
|---|---|---|
| 人工参考判断 | 逐问结论是否有原文依据，范围是否正确，冲突和缺口是否如实 | 不能因为“是人工写的”就默认正确 |
| 系统结果 | 系统回答、引用、主张、冲突和缺口是否满足同一标准 | 不能只和参考文字比对，必须回到原始材料 |
| 对照记录 | 两者在逐问、逐主张、逐引用上的差异是否被正确描述 | 不能把“与参考一致”当作事实正确 |

原则：

- **材料优先。** 人工参考和系统输出都不是天然标准；冲突时回到原始来源。
- **逐原子问题。** 不以整段文字“看起来差不多”判定通过。
- **不设加权总分、不要求置信度百分比。** 使用逐项结论和阻断性错误；这是交接规范明确不要求的评分表。
- **未知可以接受，伪装不可以。** 如实写未知、失败、缺口不扣分；把未知写成确定结论是阻断错误。
- **评估对象分离。** 系统失败不自动使案例材料无效；参考错误也不自动使系统错误。

## 1. 结论等级

| 结论 | 条件 |
|---|---|
| `通过` | 所有适用标准通过；无阻断性错误；非阻断缺陷不影响结论 |
| `有条件通过` | 无阻断性错误；存在非阻断缺陷或未关闭的小范围问题；必须列出条件、影响和关闭期限 |
| `不通过` | 任一阻断性错误成立；或关键标准失败且无法用范围说明补救 |
| `无法评估` | 缺少必要前提：没有真实参考、没有系统运行、没有快照、没有复核，或对照对象不可比。**不是通过。** |

`有条件通过` 不能当成最终通过；在条件关闭前，索引中的评估结论应保留为 `有条件通过`。

## 2. 统一标准

| ID | 标准 | 核心检查 | 阻断性 |
|---|---|---|---|
| G1 | 产品身份及版本正确性 | 产品、官网、版本、套餐、地区、账号类型是否与问题一致；证据是否适用于同一对象 | 是 |
| G2 | 事实正确性 | 每个原子问题的答案是否与事实基准日内的一手材料一致 | 是（关键事实） |
| G3 | 关键结论的引用有效性 | 每个关键结论是否有可定位的 `READ` 证据；引用 ID、原句、定位、hash 是否成立 | 是 |
| G4 | 引用原句是否支持结论 | 原句在主语、谓语、范围、极性、模态和时间上是否真的支持该句 | 是 |
| G5 | 冲突与证据缺口的表达 | 冲突是否保留，缺口类型和检索范围是否正确，失败是否被写成“没有” | 是 |
| G6 | 是否存在过度推断 | 是否把个别报告、官方宣称、同源转载、有限检索扩大为普遍事实 | 是（关键结论） |
| G7 | 来源独立性 | 同源是否识别；独立来源是否按源头计数 | 是（同源当独立） |
| G8 | 六项材料完整性 | 六项是否齐全；未知和失败是否如实保留 | 是（关键项缺失） |
| G9 | 状态与过程诚实 | 状态、运行 ID、快照、失败、确认、复核是否与实际一致 | 是（伪造状态） |
| G10 | 参考隔离 | 系统运行是否未读取参考判断、预期主张或评估材料 | 是（泄漏） |
| G11 | 可复现性 | 第二个人能否按 URL、定位、时间和 hash 找回原句 | 否；关键不可复现升级为阻断 |
| G12 | 回答范围与意图 | 是否回答了用户问的；是否越界给建议或回避关键问题 | 否；关键偏离可升级为阻断 |

## 3. 逐项检查

### G1 产品身份及版本正确性

检查：

- 产品名、官网、版本、套餐、地区、账号类型是否与用户问题一致。
- 每条证据的 `productVersion`／`plan`／地区是否适用于该主张。
- 是否把 Free 的结论套到 Pro，把某地区页面套到另一地区，把旧版本文档当成当前版本。
- 同名产品、改名、收购、不同国家站点是否消歧。
- 问题本身有歧义时，是否记录并明确本次范围，而不是静默缩窄。

通过条件：关键主张的产品、版本、套餐、地区与证据对象一致；未知版本在 `scope` 中明确，且结论不冒充版本特定事实。

阻断条件：关键结论使用了错误产品／版本／套餐／地区；把付费版权益写成免费版；把某地区政策写成全球；用旧版本文档证明当前版本。

注意：版本未知不一定阻断。如果结论明确写“版本未知，以下仅适用于该页面所述套餐”，并把它作为缺口，可能通过；但不能写成“当前所有版本都如此”。

### G2 事实正确性

检查：

- 每个 `Q-ID` 是否有明确答案；是否只回答了容易的部分。
- 数值、单位、重置方式、消耗方式、套餐名、地区、日期、能力名称是否与原文一致。
- 是否交叉核对官方定价页、帮助中心、文档、更新记录；有冲突时是否保留。
- 是否把旧页面当当前页面；是否记录“最后更新”或生效时间。
- 是否把“官方写明”误写成“实际可用”；是否把“最多”写成“固定”。

通过条件：关键事实与事实基准日内的材料一致；范围外的推断已标明；官方页面之间的不一致已记录。

阻断条件：关键事实错误（额度数字、重置方式、套餐、地区、日期、能力方向）；答案与自己的引用矛盾；用过期材料证明当前事实且未说明。

注意：拼写、标点、不影响含义的轻微措辞差异不是阻断项；但改变条件、范围或极性的“轻微改写”是阻断项。

### G3 关键结论的引用有效性

检查：

- 每个关键结论是否至少有一条 `READ` 证据；背景句是否明确标为背景。
- 引用 marker 是否出现在正文；`claimIds`／`evidenceIds` 是否存在于同一快照。
- `quotes.originalExcerpt` 是否与证据原句逐字符一致；是否覆盖全部 `evidenceIds`。
- `READ` 证据是否有原句、定位、SHA-256、无读取错误。
- 是否把 `SNIPPET_ONLY`、译文、失败页面当成引用。
- 是否引用了另一个快照或另一个调查的 ID。

通过条件：关键结论都有可定位的 READ 证据；引用结构完整；原句逐字符匹配；定位和 hash 足以复核。

阻断条件：关键结论无引用；引用指向非 READ 证据；引用 ID 悬空；原句被改写、翻译或拼接；READ 缺定位／hash；引用另一个产品／版本的证据。

注意：没有引用的背景介绍、方法论说明可以存在，但不能承载关键结论。

### G4 引用原句是否支持结论

检查原句与结论的以下维度：

- **主语**：是谁说的、关于哪个产品。
- **谓语**：到底断言了什么。
- **范围**：版本、套餐、地区、时间、使用场景。
- **极性**：支持还是反驳；肯定还是否定。
- **模态**：事实、官方宣称、使用者报告、观点、可能性。
- **条件**：是否删掉了“在……情况下”“最多”“部分”“测试中”等限定。

通过条件：原句在上下文中直接支持该结论，范围和条件匹配；官方宣称只被用来证明“官方这样说”，没有被当作独立实测；使用者报告只被用来证明“该使用者报告”，没有被扩大为普遍事实。

阻断条件：原句与结论无关；原句支持相反方向；原句谈的是另一个产品／版本／套餐／地区；删掉条件后改变含义；把译文当原话；把官方 benchmark 当第三方实测；把“可能”写成“已经”。

注意：`CONTEXT` 关系可以引用不直接支持结论的材料，但必须标明是背景；错误在于把它写成 `SUPPORTS`。

### G5 冲突与证据缺口的表达

检查：

- 已知的反例、相反报告、官方页面之间的矛盾是否保留。
- 冲突是否至少包含一条主张和两条不同证据；是否写清双方条件和未解决点。
- 缺口是否使用 `NOT_FETCHED`／`READ_FAILED`／`NOT_FOUND_IN_SCOPE`／`IDENTITY_UNCLEAR`／`INSUFFICIENT_EVIDENCE`。
- `NOT_FOUND_IN_SCOPE` 是否有明确 `searchScope`（平台、查询词、语言、时间窗）。
- `READ_FAILED` 是否保留真实原因；未知是否写 `UNKNOWN`。
- 是否把读取失败、登录限制、付费墙写成“没有讨论”或“没有资料”。
- 是否用“没有记录缺口”暗示“没有未知”。

通过条件：冲突和缺口与材料一致；不能解释的冲突明确保留；缺口类型正确、范围明确；失败和未获取可区分。

阻断条件：把 READ_FAILED／RESTRICTED 写成“没有讨论”；用有限检索断言“整个互联网没有”；隐藏已知反例；冲突缺少一方或两条证据；`NOT_FOUND_IN_SCOPE` 无检索范围；把冲突降成“证据不足”以逃避判断。

注意：未解决的冲突本身不是缺陷；隐藏冲突才是。`INSUFFICIENT_EVIDENCE` 是合法结论，不是失败。

### G6 是否存在过度推断

检查：

- 是否把一条使用者报告写成“开发者普遍认为”“大家都遇到”。
- 是否把官方宣称写成“已证实”“独立验证”。
- 是否把官方 benchmark 写成“实际性能最好”。
- 是否把有限范围检索写成“没有这种功能”“没人讨论”“不存在”。
- 是否把当前版本的表现外推到所有版本、所有地区、所有用户。
- 是否把相关性写成因果；把一次测试写成普遍结论。
- 是否在没有用户要求时给出购买建议；建议是否使用真实用户条件。
- 是否使用“证明”“确认”“必然”“从不”“全部”等超出证据的词。

通过条件：结论带有适当限定；个别报告、官方宣称、第三方材料各自的证据地位清楚；没有把未知写成确定。

阻断条件：关键结论明显超出证据范围；把同源转载当多方证实；把官方自称当独立事实；把有限检索当全球不存在；把个别体验当普遍事实；无用户条件却给适配建议。

注意：明确标注为“假设”“待验证”“个人观点”的表述，如果不冒充事实，可以不阻断；但不能用标签掩盖实际断言。

### G7 来源独立性

检查：

- 是否识别同一作者跨平台、同一文章转载、同一新闻稿、同一 upstream、同一实验、同一 GitHub issue。
- `SHARED_ORIGIN` 是否有 `originGroupId` 和 `independenceReason`。
- `UNKNOWN` 是否被误计为独立。
- 独立来源数量是否按源头计，而不是按 URL／平台计。
- 是否用“多个平台都有”作为独立证实。

通过条件：同源关系有依据；独立来源按源头计数；不确定的标 `UNKNOWN` 且不计入独立支持。

阻断条件：同一作者／同一文章／同一 upstream 被当作多个独立来源；跨平台自动视为独立；用“多方证实”描述同源转载；为了凑数量把 `UNKNOWN` 算作独立。

注意：A 类事实如果只依赖官方页面，不需要强行凑独立来源；但不能声称“多源证实”。B、C 类对独立性更敏感。

### G8 六项材料完整性

检查六项：

1. 案例 ID 与产品、版本／套餐。
2. 用户问题原话 + 回答意图。
3. 证据列表：URL、原句、站点、发布时间、作者／公开身份线索、获取日期；未知和失败如实。
4. 每条证据对哪个主张支持／反驳／无关；同源说明。
5. 冲突与缺口：区分未取得、读取失败、明确范围内未找到。
6. 核查时间与核查人；独立复核另记人、时间、判断与依据。

通过条件：六项齐全；未知字段明确写未知；失败保留 URL 和真实状态；没有用占位符冒充内容。

阻断条件：缺少关键项；用虚构内容补空；把未知写成确定；没有获取时间；没有主张关系；没有冲突／缺口记录且实际存在；没有复核记录却声称已复核。

注意：作者、发布时间确实未知时写“未知”可以通过；空白不写不行。

### G9 状态与过程诚实

检查：

- 材料状态、系统状态、复核状态是否与实际文件一致。
- 系统运行是否有真实 `investigation_id`；成功是否有真实 `snapshot_id` 和版本。
- 失败是否保留真实错误；是否把 `PROVIDER_NOT_CONFIGURED` 写成“没有找到信息”。
- 是否直接插数据库、手改状态或伪造成功。
- 是否把测试夹具、附录 A 虚构样例、历史占位案例当作真实案例。
- 人工确认和独立复核是否有真实签署。

通过条件：状态与证据一致；运行 ID／快照 ID 可追溯；失败如实；没有夹具冒充。

阻断条件：未运行标已运行；无快照标成功；未复核标已复核；伪造 ID；手改数据库状态；把夹具当真实案例；把参考判断填成系统输出。

注意：系统失败是诚实记录，不是违规；它可能使“系统对照完成”不成立，但不影响材料真实性。

### G10 参考隔离

检查：

- 系统输入是否只有问题原文和必要的真实身份确认依据。
- 是否把 `reference.md`、预期主张、证据清单、评估标准、复核意见送入问题、提示词、检索词或身份依据。
- 是否在系统运行前用参考结论改写问题。
- 对照是否在快照发布后进行；离线工具是否只读不回灌。
- 复核人是否先独立判读，再看参考和系统结果。

通过条件：运行输入清单完整；`reference_used: false`；问题 hash 与案例一致；复核顺序有记录。

阻断条件：参考内容进入系统输入；用参考结论反向填充系统输出；先看参考再声称独立复核；把评估材料作为检索线索。

注意：离线对照工具同时读取快照和参考，不算泄漏，前提是它不把参考回灌到调查、检索或生成。

### G11 可复现性

检查：

- URL 是否直达原始页面；是否只是搜索结果或聚合页。
- 定位是否具体到段落、评论、页码、时间点。
- 获取时间、发布时间、hash 是否记录。
- 另一个人能否按记录找回原句；页面变化后是否有归档或说明。

通过条件：关键证据可复找；定位和时间足够；页面不可达时有真实说明和已保存依据。

阻断条件：关键结论无法复找，且没有 hash／归档／定位；URL 指向首页或搜索页；定位只写“文中”。

注意：后来 404 不自动等于虚构；如果当时 `READ` 且有 hash、原句、获取时间，记录“当前不可达”即可。反过来，声称 READ 但没有 hash／定位，是阻断项。

### G12 回答范围与意图

检查：

- 是否回答了用户问的产品、版本、套餐、地区和问题。
- 是否把客观搜查强行变成推荐，或在用户要求建议时不给条件。
- 是否回避关键问题，只回答容易的部分。
- 是否塞入与问题无关的全套产品介绍。
- 建议是否使用真实用户条件；是否补造预算、用途或经验。

通过条件：回答覆盖全部原子问题；范围外内容明确标为背景；建议有真实条件和证据。

阻断条件：关键问题未回答却声称完成；改变用户问题；无用户条件却给适配建议；用泛泛介绍替代具体事实。

注意：额外背景不必然是缺陷，只要不冒充答案、不淹没关键结论。

## 4. 阻断性错误

任一阻断性错误成立，被评估对象判 `不通过`。阻断错误不能靠“其他项都很好”抵消。

| ID | 阻断性错误 | 核心判定 |
|---|---|---|
| X1 | 虚构或不可定位引用 | 引用不是来自所称来源，或无法定位 |
| X2 | 明显错误的证据关联 | 原句不支持该结论，或谈的是另一对象／范围 |
| X3 | 证据不足却断言成立 | 把个别、官方、有限或未读材料写成确定事实 |
| X4 | 同源转载视为独立证实 | 同一作者／文章／上游被计为多个独立来源 |
| X5 | 官方宣称或 benchmark 当独立实测 | 官方自称被写成第三方验证 |
| X6 | 读取失败写成没有讨论 | 失败／限制／未获取被改写成“没有信息” |
| X7 | 身份／版本／套餐／地区错配 | 关键结论用错产品、版本、套餐或地区 |
| X8 | 过度推断／范围扩大 | 关键结论超出证据覆盖范围 |
| X9 | 参考泄漏 | 参考判断或评估材料进入系统运行 |
| X10 | 状态／过程造假 | 未运行、未复核、夹具或手改数据被写成真实 |
| X11 | 红线越界 | 时政、私人身份、版权超限、负面措辞越界 |
| X12 | 冲突／缺口被隐藏或类型错误 | 已知冲突被删，或缺口类型／范围造假 |

### X1 虚构或不可定位引用

定义：URL、原句、作者、发布时间、hash 或页面内容不是实际取得的；或者引用无法回到所称来源。

例子：

- 编造一句“官方说免费版每月 100 次”，但页面没有这句话。
- 把 A 文章的句子挂到 B 文章 URL。
- 编造作者、日期或 hash。
- 标 `READ` 但没有原句、定位或 hash，实际只看了搜索摘要。
- 引用一个从未打开的页面，并用模型生成“原文”。

判定：重开 URL、搜索原句、核对 hash 和归档；无法复现即成立。

注意：页面后来 404 不等于虚构。若当时确有 `READ`、原句、定位、hash 和获取时间，记录“当前不可达”即可；但不能声称“现在仍可打开”。

### X2 明显错误的证据关联

定义：证据被用于它并不支持的结论；包括对象、范围、极性、模态或条件错误。

例子：

- 用 Pro 套餐页面证明 Free 套餐有导出。
- 用 2024 年版本报告证明 2026 年版本仍如此。
- 原句说“I could not export”，被写成“supports export”。
- 原句说“in some cases”，被写成“always”。
- 把译文当作 `originalExcerpt`。
- 用 GitHub issue 的提交者描述证明维护者已确认。

判定：逐项检查主语、谓语、范围、极性、模态、条件；不匹配即成立。

注意：`CONTEXT` 关系可以引用不直接支持结论的材料；错误在于标成 `SUPPORTS`／`REFUTES`。

### X3 证据不足却断言成立

定义：材料不足以支持确定结论，却被写成 `SUPPORTED`、`已证实`、`确定`、`普遍`。

例子：

- 一条 HN 评论 → “开发者普遍认为”。
- 官方宣称 → “事实已被验证”。
- 三个查询没找到 → “互联网上没有”。
- 页面 403 → “该功能不存在”。
- 一个 benchmark → “性能最好”。
- 多个模型意见一致 → “事实已确认”。

判定：看结论强度是否超过证据数量、独立性、范围和读取状态。

注意：写 `INSUFFICIENT`、`DISPUTED`、`在已查范围内未找到` 是正确的，不构成阻断。

### X4 同源转载视为独立证实

定义：同一作者跨平台、同一文章转载、同一新闻稿、同一 upstream 数据、同一实验、同一 issue 被当作多个独立来源。

例子：

- 作者在 X、HN、博客各发一次，被计为 3 个独立来源。
- 同一篇文章被 4 个站点转载，写成“4 家媒体证实”。
- 多个帖子都引用同一个 GitHub issue，写成“多方报告”。
- 同一厂商新闻稿被多家媒体改写，写成“独立报道”。

判定：检查作者、发布时间、原文措辞、upstream、实验数据、引用链；同源即成立。

注意：无法确认时标 `UNKNOWN`，不计入独立支持；不能为了凑数判独立。

### X5 官方宣称或 benchmark 当独立实测

定义：官方博客、定价页、benchmark、新闻稿被写成独立验证或第三方实测。

例子：

- “官方 benchmark 显示最快” → “实测最快”。
- “官方称支持 X” → “X 已被证实”。
- 官方文档的功能列表 → “用户实际可用”。

判定：看 `sourceType`／`contentKind` 和句子归属；官方材料只能证明“官方这样说”。

注意：官方材料可以作为事实基线（例如官方定价页写明的价格），但不能证明独立性能或普遍实际体验。

### X6 读取失败写成没有讨论

定义：`FAILED`／`RESTRICTED`／`NOT_FETCHED` 被改写成“没有相关信息”“没人讨论”“不存在”。

例子：

- 403 → “Reddit 上没有讨论”。
- 付费墙 → “官方没有说明”。
- 超时 → “没有找到任何来源”。
- 未尝试 → “没有资料”。

判定：看 `readStatus`、`readError`、检索记录；失败与“未找到”必须区分。

注意：在明确范围内检索后未找到，可以写“在已查范围内未找到”，并写 `searchScope`；不能写“整个互联网没有”。

### X7 身份／版本／套餐／地区错配

定义：关键结论使用了错误的产品、版本、套餐、地区或账号类型。

例子：

- 把 Team 的额度写成 Free。
- 把美国区价格写成中国区。
- 把旧版本文档当成当前版本。
- 同名产品未消歧，查了另一个产品。
- 把“免费试用”写成“免费版”。

判定：核对身份依据、证据元数据、主张 scope；错配即成立。

注意：版本未知但结论明确限定为“该页面所述套餐、版本未知”可以不阻断；不能把未知版本写成“当前版本”。

### X8 过度推断／范围扩大

定义：关键结论超出证据覆盖的产品、版本、地区、时间、样本或场景。

例子：

- 单个用户报告 → “所有开发者”。
- 一次测试 → “普遍性能”。
- 当前版本 → “一直如此”。
- 某地区 → “全球”。
- 相关性 → 因果。
- 没有用户要求 → 购买建议。

判定：检查限定词、scope、样本和结论强度。

注意：明确标注的假设或个人观点，如果不冒充事实，可以不阻断；但不能用“可能”包装确定断言。

### X9 参考泄漏

定义：系统运行读取了人工参考答案、预期主张、证据清单、评估标准或复核意见；或用参考反向填充系统输出。

例子：

- 把 `reference.md` 的内容放进问题或提示词。
- 把预期 URL 列表交给检索提供方。
- 系统运行前先看参考，再“复现”答案。
- 用参考结论修改系统快照或回答。
- 复核人先看参考，再声称独立判读。

判定：检查运行输入清单、问题 hash、提示词、检索记录、复核顺序；泄漏即成立。

注意：快照发布后的离线对照可以同时读两者；只要不回灌到调查、检索或生成，就不算泄漏。

### X10 状态／过程造假

定义：未发生的运行、快照、确认或复核被写成已发生；或使用测试夹具、虚构样例、手改数据库冒充真实结果。

例子：

- 没有调查 ID 却写“系统已运行”。
- 没有快照 ID 却写“成功”。
- 没有丙的签署却写“已独立复核”。
- 把 `tests/fixtures` 当真实案例。
- 直接改数据库状态为 `SUCCEEDED`。
- 把附录 A 虚构样例计入 D1。

判定：核对 ID、快照、错误、签署、文件来源；不一致即成立。

注意：系统失败、缺少快照、未复核都是允许的真实状态；造假是把它们写成成功。

### X11 红线越界

定义：违反时政、私人身份、版权摘录或负面措辞红线。

例子：

- 调查具体个人的私人身份、联系方式、私德。
- 摘录超过 300 字符或整段转载。
- 写“虚假宣传”“骗子”“割韭菜”。
- 把官方宣称写成欺骗。
- 采集与核查无关的个人画像。

判定：按 [核查与交接规范](../docs/reference/队友交接包/策划/核查与交接规范.md) 的红线检查；越界即成立。

注意：公开作者名／账号和公开角色线索是允许的；不要延伸个人画像。

### X12 冲突／缺口被隐藏或类型错误

定义：已知冲突被删除或弱化；缺口类型、范围或原因与实际不符。

例子：

- 两条相反报告只保留一条。
- 把 `READ_FAILED` 写成 `NOT_FOUND_IN_SCOPE`。
- `NOT_FOUND_IN_SCOPE` 没有 `searchScope`。
- 把“有材料但不足以判断”写成“没有资料”。
- 冲突只列一条证据。
- 用“证据不足”掩盖明确的反驳。

判定：核对冲突双方、证据数量、缺口枚举和检索范围；不实即成立。

注意：未解决冲突可以保留为 `DISPUTED`；这不是阻断。

## 5. 评估程序

1. **冻结对象。** 记录案例文件版本、参考文件版本、来源获取时间和 hash、系统快照 ID／版本。评估过程中不换材料。
2. **检查前提。** 六项是否齐全；身份是否确认；参考是否由乙确认；评估系统时是否有真实运行；最终结论是否有丙复核。
3. **先查 G1。** 身份、版本、套餐、地区错配时，停止下游评估，要求重做；不要基于错误身份给高分。
4. **逐问查 G2。** 每个 `Q-ID` 单独对照材料，记录答案、依据、范围、缺口。
5. **逐结论查 G3／G4。** 每个关键结论和每条引用单独检查结构有效性和语义支持。
6. **查 G5／G6／G7。** 冲突、缺口、过度推断、独立性逐项记录。
7. **查 G8／G9／G10。** 六项完整性、状态诚实、参考隔离。
8. **查 G11／G12。** 可复现性和回答范围；关键不可复现或关键偏离升级为阻断。
9. **跑阻断清单 X1–X12。** 任一成立即 `不通过`；不要用其他项抵扣。
10. **给结论。** 按对象分别记录；对照记录单独写；最后更新索引。

评估顺序的理由：身份错则证据全错；引用结构错则语义支持无从谈起；先材料后系统，避免用系统输出倒推参考。

## 6. 记录模板

每个被评估对象各填一张：

| 标准 | 结论 | 依据 | 备注 |

| G2 事实 | 通过／部分／不通过／N/A | 具体 Q-ID／E-ID | 关键事实逐条 |
| G3 引用有效 | 通过／部分／不通过／N/A | marker／E-ID／hash | 悬空或缺失 |
| G4 原句支持 | 通过／部分／不通过／N/A | 原句关键词／范围 | 语义问题 |
| G5 冲突／缺口 | 通过／部分／不通过／N/A | X-ID／G-ID | 类型和范围 |
| G6 过度推断 | 通过／部分／不通过／N/A | 具体句子 | 限定词 |

| G8 六项完整 | 通过／部分／不通过／N/A | 缺项 | 未知是否如实 |

## 7. 边界情况

| 情况 | 处理 |
|---|---|
| 系统未配置，运行失败 | 记 `系统已运行（失败）`、真实错误、无快照；系统评估为 `无法评估`，不能写“没有找到信息” |
| 来源现在 404，但当时已 READ | 保留原句、hash、获取时间；标“当前不可达”；不判虚构；不声称现在可打开 |
| 付费墙／登录限制 | `RESTRICTED`；保留限制原因；不用摘要当原句；缺口写 `READ_FAILED` 或 `RESTRICTED` 对应说明 |
| 只有机翻 | 原文和译文分列；引用只用原文；译文错误不改变原句，但可能影响理解，需人工核对 |
| 官方页面互相矛盾 | 两条都保留；写清版本／日期；不能静默选一个；必要时记冲突 |
| 产品改名／被收购 | 在身份依据中说明；旧名和新名映射；不能把两个产品混为一个 |
| 免费额度变更 | 记录变更前后和生效时间；结论限定事实适用期；不能把旧额度写成当前 |
| 地区差异 | 每个地区单独主张；不能由美国站推中国区；地区未知写缺口 |
| 使用者报告被删除 | 保留 URL、获取时间、hash、原句；标“当前不可达”；不能补造 |
| 同一作者不同账号 | 有公开证据才判同源；不确定写 `UNKNOWN`；不做人肉关联 |
| AI 生成内容 | 标为 AI 生成或未知；不能当独立使用者报告；除非有真实作者和场景 |
| 系统对、参考错 | 以材料为准，修正参考并记录；不能为了维护参考而改系统 |
| 系统错、参考对 | 系统评估 `不通过`，列出阻断项；案例材料仍可有效 |
| 没找到真实冲突 | B 类明确报告“真实冲突”验收项未完成；不能制造冲突；可保留检索范围和缺口 |
| 没找到独立来源 | C 类写“独立来源数为 0／1”；不能把同源算独立；结论可以是证据不足 |
| 历史快照 | 标版本和生成时间；不能称为本次最新成功；对照时说明版本差异 |
