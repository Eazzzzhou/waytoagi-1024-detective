# B 类 · 海外开发者观点与真实冲突

版本：v0.1（阶段 1）· 2026-10-24

> 状态：B-01 已选定 **Devin（Cognition）**；真实官方材料、海外原文、人工参考草稿已建立，**待乙确认**；系统未运行、丙未复核。C 类未开始。B 类是 D1“至少一案含海外原句与真实冲突”的主要承载类型。

## 1. 问题模板

> `官方称 [产品] 在 [能力] 上有优势，但 Hacker News、GitHub 或 X 上的实际使用报告是否支持这一说法？`

回答意图默认是**客观搜查**：核对官方原话与范围，列出海外实际使用报告，说明支持、反驳、无关和未解决冲突。不是给产品打分，也不是替官方做营销复核。

## 2. 必须回答的原子问题

| ID | 原子问题 | 不能省略的原因 |
|---|---|---|
| B-Q1 | 官方原话是什么？能力、版本、场景、benchmark 条件和时间范围是什么？ | 没有原话就无法判断“是否支持” |
| B-Q2 | 海外开发者具体报告了什么？作者、平台、直达 URL、发布时间、版本、场景是什么？ | 区分具体报告与泛泛评论 |
| B-Q3 | 哪些报告支持、哪些反驳、哪些在谈另一个能力或版本？ | 防止把无关讨论算作支持 |
| B-Q4 | 冲突能否由版本、场景、样本、方法或时间解释？不能解释的部分是什么？ | 真实冲突要保留条件 |
| B-Q5 | 来源是否独立？是否存在同一作者跨发、同一文章转载、同一实验或同一上游？ | 防止同源当多方证实 |
| B-Q6 | 在现有证据下，官方说法能被支持到什么程度，不能支持到什么程度？ | 结论必须带范围 |

## 3. 证据结构

B 类至少应覆盖：

| 证据类型 | 作用 | 注意 |
|---|---|---|
| 官方宣称原文 | 确定被检验的说法 | 标 `OFFICIAL_CLAIM`；官方 benchmark 不是独立实测 |
| 海外社区原文 | 实际使用报告、问题、对比 | 直达 URL、作者、时间、版本、场景；必须 `READ` |
| 官方后续回应／修复记录 | 解释冲突或版本差异 | 回应不等于问题普遍存在 |
| 独立第三方测试（如有） | 交叉验证 | 记录方法、样本、版本；不能与官方 benchmark 混为一谈 |

硬要求：

- 至少一条官方宣称 `READ`，至少一条海外原文 `READ`；搜索摘要、翻译、二手转述不能充当原句。
- 海外原文要保留原句和译文；引用只用原句。
- 冲突至少涉及一条主张和两条不同证据；不能只列一方。
- 如果检索后没有找到真实冲突，写清检索范围、失败状态，并明确“B 类真实冲突验收项未完成”；不得制造冲突。
- 官方 benchmark 只能证明“官方这样测／这样说”，不能证明独立性能。

## 4. 类型门槛

B 类案例可以进入评估，必须同时满足：

1. 官方宣称的原话、版本、能力范围、时间明确。
2. 至少一条海外开发者原文已 `READ`，可定位。
3. 支持与反驳材料都经过同一主张的核对，不是各说各话。
4. 冲突有条件分析；不能解释的部分保留。
5. 同源关系已识别；独立来源按源头计数。
6. 结论强度不超过证据；没有把个别报告写成普遍事实。
7. 参考判断由乙确认；系统运行与独立复核按通用流程完成。

## 5. 常见阻断错误

- 只有官方博客／benchmark，没有海外原文，却写“海外开发者支持”。
- 只有一条 HN 评论，写“开发者普遍认为”。
- 把 GitHub issue 的提交者描述写成维护者确认。
- 把“有人报告问题”写成“所有用户都遇到”。
- 把官方 benchmark 写成第三方实测。
- 把不同版本、不同场景的报告合并成一个结论。
- 只保留支持方，删掉反例。
- 把 X 发帖、HN 转发、中文转载当成三个独立来源。
- 把搜索摘要当海外原句。
- 没找到冲突就编造冲突，或把“没找到”写成“没有冲突”。

## 6. 选题检查

选题时先回答这些问题；任一关键项为“否”就不要把该题计入正式 B 案：

- [ ] 产品有一个明确、可引用的官方能力宣称？
- [ ] 官方宣称有版本、场景或 benchmark 条件，能界定范围？
- [ ] Hacker News、GitHub、X 或其他海外平台有可访问的相关原文？
- [ ] 至少有一条具体使用报告，而不是只有营销转述？
- [ ] 存在至少一个潜在反例、差异或冲突线索？（没有则准备如实报告未完成）
- [ ] 能取得原文和作者／时间／定位，而不是只有摘要？
- [ ] 能判断同源关系，至少能识别明显的同作者／同文章转载？
- [ ] 用户问题原话已经拿到，不是自己编的模板？
