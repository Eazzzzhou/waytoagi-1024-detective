# D1 案例规范

版本：v0.1（阶段 1）· 2026-10-24 · 负责人：乙

## 0. 效力与来源

本规范把仓库中已有的 D1 要求落成可填写的案例结构，不替代原要求。

- 六项材料要求来自 [核查与交接规范](../docs/reference/队友交接包/策划/核查与交接规范.md) 的“交付需要带上什么”。六项仍是必填，不因本规范新增字段而减少。
- 三案数量、至少一案含海外原句与真实冲突、Markdown 交接、丙独立复核，来自 [迭代与任务派单](../docs/reference/队友交接包/策划/迭代与任务派单.md) 的 D1 交付卡。
- 红线、限定来源和负面措辞要求同见上述规范；本规范只做操作化，不放宽。
- 本规范不改变 `src/contracts` 的 Zod 契约。D1 的 `region`、事实适用期、系统对照等字段是案例记录字段；需要进入运行时快照时，必须另行走共享契约和三人对齐，不能在案例文档里私自扩展快照 JSON。

## 1. 三类案例

| 类型 | 问题模板 | 要解决的核心 | 类型门槛 |
|---|---|---|---|
| A 功能、套餐与版本事实 | `[产品] 免费版的额度是多少？按月重置、按次消耗，还是一次性额度？` | 在明确产品、版本、套餐、地区和时间内，额度数值及计量方式是什么 | 至少一条官方 READ 依据；额度数值与重置／消耗方式必须分别回答 |
| B 海外开发者观点与真实冲突 | `官方称 [产品] 在 [能力] 上有优势，但 Hacker News、GitHub 或 X 上的实际使用报告是否支持这一说法？` | 官方宣称的原话与范围是什么，海外实际使用报告支持、反驳还是谈的是另一件事 | 至少一条官方宣称 READ、至少一条海外原文 READ；真实冲突要么找到并保留，要么如实报告未找到 |
| C 来源关系、转载与证据不足 | `关于 [产品] 支持 [功能] 的几条说法，哪些是独立来源，哪些只是同一作者或同一文章的转载？` | 说法的源头、传播关系和独立来源数量 | 至少三条说法／来源；至少评估一组同源关系，或明确报告未发现同源 |

### 1.1 A 类：功能、套餐与版本事实

必须回答的原子问题：

| ID | 原子问题 |
|---|---|
| A-Q1 | 目标产品是否存在名为“免费版”的套餐？官方名称、适用地区、账号类型是什么？ |
| A-Q2 | 免费版额度数值是多少？计量单位是什么（次、token、积分、字符、请求等）？ |
| A-Q3 | 额度如何重置或消耗：按月重置、按次消耗、一次性额度，还是其他规则？ |
| A-Q4 | 该额度适用于哪个版本、套餐、地区、账号类型或计费周期？ |
| A-Q5 | 官方口径的发布时间、最后更新时间或生效时间是什么？ |
| A-Q6 | 官方定价页、帮助中心、文档或更新记录之间是否存在不一致？ |

类型门槛与常见错误：

- 只写“免费”不给数值，不算回答额度。
- 把 Pro／Team 的额度套到免费版，或把某地区价格／额度套到另一地区，属于身份或范围错配。
- 把“每月赠送”写成“永久”“一次性”，或反过来，属于事实错误。
- 官方页面写的是“up to”／“最多”时，不能改写成固定额度；条件必须保留。
- 官方额度与实际可用量是两件事；没有实测时不能声称“实际一定能用满”。

### 1.2 B 类：海外开发者观点与真实冲突

必须回答的原子问题：

| ID | 原子问题 |
|---|---|
| B-Q1 | 官方原话是什么？它声称的能力、版本、场景、benchmark 条件和时间范围是什么？ |
| B-Q2 | 海外开发者具体报告了什么？作者、平台、直达 URL、发布时间、版本和使用场景是什么？ |
| B-Q3 | 哪些报告支持官方说法，哪些反驳，哪些其实在谈另一个能力或另一个版本？ |
| B-Q4 | 冲突能否由版本、场景、样本、方法或时间解释？不能解释的部分是什么？ |
| B-Q5 | 这些来源是否独立？是否存在同一作者跨发、同一文章转载、同一实验或同一上游？ |
| B-Q6 | 在现有证据下，官方说法能被支持到什么程度，不能支持到什么程度？ |

类型门槛与常见错误：

- 只有官方 benchmark 或官方博客，没有第三方／使用者原文：B 类未完成，不能把官方自称当独立实测。
- 只有一条 HN 评论：只能写“有使用者报告”，不能写“开发者普遍认为”或“已被证实”。
- GitHub issue 证明“有人报告了问题”，不自动证明维护者确认、已修复或所有用户都遇到。
- 海外原文必须 READ；搜索摘要、翻译、二手转述不能充当原句。
- 真实冲突必须保留双方原句、条件和未解决点；不能为了让结论干净而删掉反例。
- 如果检索后确实没有找到冲突，写清检索范围与失败状态，并明确 B 类“真实冲突”验收项未完成；不得制造冲突。

### 1.3 C 类：来源关系、转载与证据不足

必须回答的原子问题：

| ID | 原子问题 |
|---|---|
| C-Q1 | 待核查的说法逐条原文是什么？最早出处是谁？ |
| C-Q2 | 每条说法的直达 URL、作者／账号、发布时间和定位是什么？ |
| C-Q3 | 哪些来源是同一作者、同一文章、同一 upstream、同一实验或同一新闻稿？ |
| C-Q4 | 哪些来源可以判为独立？判断依据是什么？ |
| C-Q5 | 是否存在一手来源？转载是否改变原意、删减条件或增加结论？ |
| C-Q6 | 现有证据能支持什么，证据不足的部分缺什么？ |

类型门槛与常见错误：

- 跨平台不自动独立；同一作者在 X、HN、博客、公众号跨发，仍是一个源头。
- 同一篇文章被多个站点转载、同一新闻稿被多家媒体改写、多个帖子引用同一个 GitHub issue，均按同源处理。
- 无法确认同源时写 `UNKNOWN`，不能为了凑独立来源数量而判独立。
- 独立来源数量按“源头”计，不按 URL 数或平台数计。
- 如果所有说法都来自同一上游，必须明确写“独立来源数为 0／1”，不能写“多方证实”。

## 2. 案例标识与产品身份

### 2.1 必填字段

| 字段 | 要求 |
|---|---|
| `case_id` | `A-01`／`B-01`／`C-01` 起；同一 ID 不复用 |
| `case_type` | `A`／`B`／`C`，与目录一致 |
| `product_name` | 用户问题指向的产品名；同名产品必须消歧 |
| `official_website` | 产品官方站点；没有确认则 `null`，不能拿应用商店页冒充官网 |
| `version` | 本次核查的版本；未知为 `null`，不写“最新” |
| `plan` | 套餐／档位；免费版写 `Free` 或官方名称，未知为 `null` |
| `region` | 适用地区／市场；未知为 `null`。这是 D1 记录字段，不在当前 `ProductIdentity` 契约中 |
| `account_type` | 个人／企业／教育等，若影响额度则必填；未知为 `null` |
| `identity_status` | `UNRESOLVED`／`NEEDS_CONFIRMATION`／`CONFIRMED` |
| `identity_basis` | 每项含 URL、原句、获取时间、确认理由；原句 ≤300 字符 |

### 2.2 身份规则

- 先确认“查的是哪个产品”，再确认版本、套餐、地区。身份错，后面的证据全部作废。
- 同名产品、改名、被收购、不同国家站点、不同经销商，都要在身份依据里说明。
- `CONFIRMED` 至少要有官网和一条可定位依据；仅有搜索结果标题不算确认。
- 问题本身有歧义时，记录歧义和本次采用的范围，不能静默缩窄成容易回答的问题。
- 版本与套餐分开：`Free` 是套餐，不是版本；版本未知就写 `null`，不能把当前日期当版本。
- 地区影响价格、额度、功能时，必须把地区写进主张的 `scope`；不能由美国站页面推出中国区权益。

## 3. 时间口径

时间必须区分，不能用一个“查于某日”覆盖全部含义。

| 字段 | 含义 | 填写要求 |
|---|---|---|
| 研究开始／结束 | 实际检索、打开页面、获取原文的时间窗 | 含时区 ISO 8601；显示可用 Asia/Shanghai，存储保留偏移 |
| 事实基准日 | 本次结论所依据材料截止到哪一天 | 不等于网页抓取时间；要说明“截至该日未发现更新” |
| 事实适用起／止 | 结论声称适用的产品／套餐／版本时间段 | 有官方生效日、发布说明或版本变更依据；未知则 `null` 并记缺口 |
| 来源发布时间 | 原文发布或最后更新时间 | 未知写“未知”，不能由抓取时间倒推 |
| 来源获取时间 | 实际读取或尝试读取该来源的时间 | 失败也记录尝试时间 |
| 系统运行时间 | 提交调查到终态的时间 | 与案例研究时间分开 |
| 复核时间 | 丙完成独立复核的时间 | 与乙确认时间分开 |

规则：

- “今天查到的页面这样写”只证明“在该获取时间页面这样写”，不自动证明产品在整个版本周期都如此。
- 官方页面有“Last updated”“生效日期”时，优先记录；没有时，事实适用期写明“自获取时起，至核查时未见变更”，并注明不能外推到未来。
- 套餐额度、价格、功能发生变化时，旧文和新文都要保留；不能只留新文再声称“一直如此”。
- 海外使用者报告必须记录其发布时间和适用版本；更新前后的报告不能合并成一个结论。
- 转载／转载时间不能替代原文发布时间；同源判断要看的首先是原始发布时间。

## 4. 核查范围与原子问题

### 4.1 范围声明

每个案例开头写清：

- 在范围内：产品、版本、套餐、地区、时间、语言、来源类型。
- 不在范围内：未查的版本／地区、未获取的付费墙内容、未做的实测、未覆盖的平台。
- 回答意图：`客观搜查` 或 `适配建议`；本阶段三类默认客观搜查。若用户实际要求建议，必须使用真实用户条件，不得补造预算或用途。

### 4.2 原子问题规则

- 一个问题只包含一个可判断命题；不能把“额度多少”和“如何重置”合成一句。
- 每个原子问题有 `Q-ID`，并映射到至少一个主张 `C-ID`；没有主张时说明“仅背景，不作结论”。
- 每个问题在参考判断里有明确状态：`已查明（支持）`、`已查明（反驳）`、`争议`、`证据不足`、`身份／版本不明`。
- 问题不能用“是／否”掩盖条件；例如不能只问“支持导出吗”，要带版本、套餐、地区和时间。
- 问题的答案必须能回到具体证据；不能只给归纳。

## 5. 来源与证据

### 5.1 证据单位

一条证据对应一个可直接定位的来源单元（一个页面、一条评论、一个 issue、一个视频时间点）。不要把多个 URL 合并成一条证据，也不要把同一文章的多站转载当成多条独立证据。

案例内使用 `E1`、`E2` 等本地 ID；系统快照使用 UUID。对照时建立映射，不能把 `E1` 填进系统快照 ID 字段。

### 5.2 读取状态

| 状态 | 含义 | 允许填写 | 禁止 |
|---|---|---|---|
| `READ` | 已实际读取原文 | 原句、译文、定位、hash、元数据 | 无原句／无定位／无 hash 却标 READ |
| `SNIPPET_ONLY` | 只看到搜索摘要 | URL、摘要、获取时间、元数据 | 原句、译文、定位、hash；不得用于支持／反驳 |
| `NOT_FETCHED` | 尚未尝试获取 | URL、线索、获取时间（可为尝试时间） | 原句、译文；不得写成“已读但无内容” |
| `FAILED` | 尝试读取失败 | URL、真实失败原因、尝试时间 | 原句、译文、定位、hash；不得写成“没有讨论” |
| `RESTRICTED` | 登录／付费／权限／地区限制 | URL、限制原因、尝试时间 | 原句、译文、定位、hash；不得用摘要冒充原文 |

`READ` 的硬条件与共享契约一致：有原句、有定位、有 SHA-256、无读取错误。hash 是已保存原始内容的 SHA-256 小写十六进制；没有保存原始内容就不要标 `READ`，改用 `SNIPPET_ONLY` 或 `NOT_FETCHED`。

### 5.3 原句、译文与定位

- 原句逐字符保留，不改拼写、不统一空格、不补标点；最多 300 字符，只摘关键句，不整段转载。
- 译文单独字段，标“译文（非原话）”；译文不能进入 `originalExcerpt`，也不能作为引用原句。
- 定位用 `TEXT`／`COMMENT`／`PAGE`／`TIMECODE`：段落标题或编号、评论 ID、页码、视频时间点等，必须能让第二个人复找到。
- `context` 写必要上下文（前后句、讨论串主题、版本条件），不能用来偷偷补原句没有的意思。
- 省略号只能在删减不改变含义时使用；不能把条件句删成断言。
- 原文是外语时，原句和译文都要保留；只给译文不算满足“原句可定位”。

### 5.4 来源元数据

必填：URL、站点名、标题（可空）、作者／公开账号（可空）、发布时间（可空）、获取时间、语言、`sourceType`、`contentKind`、适用版本／套餐、读取状态。

| 字段 | 取值 | 规则 |
|---|---|---|
| `sourceType` | `OFFICIAL`／`COMMUNITY`／`THIRD_PARTY`／`UNKNOWN` | 只说明来源归属，不说明内容真假 |
| `contentKind` | `FACT`／`OFFICIAL_CLAIM`／`USER_REPORT`／`OPINION`／`UNKNOWN` | 官方来源也可以是 `OFFICIAL_CLAIM`；使用者报告不是普遍事实 |
| 作者 | 公开姓名／账号／公开角色线索 | 不调查私人身份、联系方式、私德；不延伸个人画像 |
| 时间 | 发布时间／最后更新时间 | 未知写“未知”，不猜 |
| 版本／套餐 | 该来源适用的版本／套餐 | 不明写 `null`；不能默认等于问题中的版本 |

其他规则：

- URL 用直达页，不用搜索结果页、短链或聚合页；有归档链接时另记，但归档不能替代原始出处。
- 官方 benchmark、官方博客、官方定价页都属于官方材料；官方 benchmark 不是独立实测。
- 同一文章多站转载：选一个主记录，其余写 `upstreamUrl` 和 `originGroupId`；不要重复计入独立支持。
- 页面已删除或后来不可达：保留原 URL、获取时间、hash 和“当前不可达”的说明；不能因此改写原句或声称从未存在。
- 引用负面结论时，写“在已查范围内未找到支持该说法的公开来源”或“该说法与当前官方文档不一致”，不写“虚假宣传”“骗子”“割韭菜”。

### 5.5 同源与独立性

| 字段 | 要求 |
|---|---|
| `upstreamUrl` | 已知上游原文；未知 `null` |
| `independence` | `INDEPENDENT`／`SHARED_ORIGIN`／`UNKNOWN` |
| `originGroupId` | `SHARED_ORIGIN` 必填；同一源头共用一个组 ID |
| `independenceReason` | 非 `UNKNOWN` 必填；说明作者、文章、实验、数据或转载关系 |

判定要点：

- 同作者跨平台、同文章转载、同新闻稿、同 upstream 数据、同一次测试、同一 GitHub issue 被反复引用：同源。
- 跨平台、不同作者但引用同一来源：仍同源。
- 不同作者、不同时间、各自独立测试：才可能独立；仍要说明依据。
- 不确定时写 `UNKNOWN`，不要计入独立支持数量。
- 独立来源数量按 `originGroupId` 计，不按 URL 或平台数计。

## 6. 主张、关系、冲突与缺口

### 6.1 主张

| 字段 | 要求 |
|---|---|
| `C-ID` | 案例内唯一，如 `C1` |
| `statement` | 单条原子主张；一句只断言一件事 |
| `kind` | `FACT`／`OFFICIAL_CLAIM`／`USER_REPORT`／`OPINION` |
| `verificationStatus` | `SUPPORTED`／`REFUTED`／`DISPUTED`／`INSUFFICIENT`／`UNVERIFIED` |
| `verificationReason` | 为什么是这个状态；引用了哪些 E；范围是否匹配 |
| `scope` | 版本、套餐、地区、时间、使用场景；未知可空，但关键主张不应空 |
| `answersQuestion` | 对应 `Q-ID` |

状态含义：

- `SUPPORTED`：至少一条 READ 证据直接支持，且范围匹配；反例已处理或明确保留。
- `REFUTED`：至少一条 READ 证据直接反驳，且范围匹配。
- `DISPUTED`：有可信证据支持相反方向，冲突未解决；不能强行选一边。
- `INSUFFICIENT`：有材料但不能决定；写清缺什么。
- `UNVERIFIED`：尚未评估；最终案例不应大量停留在此状态。

### 6.2 证据关系

| 关系 | 含义 |
|---|---|
| `SUPPORTS` | 该证据直接支持该主张 |
| `REFUTES` | 该证据直接反驳该主张 |
| `CONTEXT` | 提供背景，不直接支持或反驳 |
| `IRRELEVANT` | 看似相关但实际无关；要说明为什么 |
| `UNCERTAIN` | 无法判断；要说明缺什么 |

- 只有 `READ` 证据可以 `SUPPORTS`／`REFUTES`；摘要、译文、失败页面只能 `CONTEXT`／`UNCERTAIN`。
- 同一证据可对应多个主张，但每个关系都要单独写理由，不能复制一句“支持”。
- 关系理由要回答“原句的哪个部分、在什么范围内支持／反驳”，不能只写“有关”。

### 6.3 冲突

冲突记录至少包含：`X-ID`、涉及主张、至少两条不同证据、冲突描述、处理结果。

- 冲突描述要写清双方各说什么、各自适用版本／场景／时间。
- 能解释的写条件；不能解释的 `resolution` 留空，写“尚不能消除”。
- 不得把冲突删掉只留一方；也不得用“各有一理”代替具体差异。
- 冲突不等于证据不足：有明确相反证据时用 `DISPUTED`，不要降成 `INSUFFICIENT` 逃避判断。

### 6.4 缺口

缺口类型必须使用共享契约的枚举：

| 类型 | 用法 |
|---|---|
| `NOT_FETCHED` | 知道有材料但尚未获取 |
| `READ_FAILED` | 尝试读取失败；写真实原因，未知写 `UNKNOWN` |
| `NOT_FOUND_IN_SCOPE` | 在明确范围内检索后未找到；必须写 `searchScope` |
| `IDENTITY_UNCLEAR` | 产品／版本／套餐／地区不能确认 |
| `INSUFFICIENT_EVIDENCE` | 有材料但不足以判断 |

- `NOT_FOUND_IN_SCOPE` 不能写成“互联网上没有”“没人讨论”；范围要写平台、查询词、语言、时间窗。
- `READ_FAILED` 不等于“没有讨论”；`NOT_FETCHED` 不等于“没有资料”。
- 缺口要绑定到具体主张；没有绑定对象的“泛泛而缺”不算合格记录。
- 没有记录缺口不等于不存在未知；评估时仍要检查是否漏记。

## 7. 人工参考判断

### 7.1 存放与隔离

人工参考判断写在同案例目录的 `reference.md`，与 `case.md` 分开。该文件：

- 只供乙确认、丙复核和离线评估使用。
- 不得作为系统运行、检索、身份确认、回答生成的输入。
- 不得把其中结论复制进问题原文、身份依据、检索词或提示词。

### 7.2 必填内容

- 每个 `Q-ID` 的参考结论与状态。
- 每个 `C-ID` 的主张类型、参考状态、理由、适用范围、对应证据。
- 关键结论所依赖的原句与定位；不能只写“见 E2”。
- 冲突与缺口的处理：哪些能解释，哪些不能。
- 不确定性：哪些结论可能因新证据改变；需要什么证据才能改变。
- 人工确认：确认人、确认时间、确认声明。
- 模型协助说明：模型做了什么（检索整理、翻译候选、表格整理），人核对了什么；不能把模型输出直接写成人工判断。

### 7.3 确认规则

- 只有乙可以填写“人工已确认”；自动化脚本、模型、其他协作者不能代填。
- 确认前必须逐条核对原句、定位、关系和范围；不能只浏览摘要后签字。
- 确认声明要明确：这是人工参考判断，不是系统输出；已核对哪些材料；仍有哪些不确定。
- 参考判断不是天然正确；丙复核可以不同意。材料与原文优先于任何人的结论。
- 不要求置信度百分比；用状态、理由和范围表达确定性。

## 8. 系统运行与对照

### 8.1 运行输入

允许输入：

- 用户问题原文（与 `case.md` 完全一致；API 仅去首尾空白）。
- 用户真实提供的身份确认依据（如有）；记录 URL、原句、时间、理由。

禁止输入：

- `reference.md`、`case.md` 的参考结论、预期主张、证据清单、评估标准、复核意见。
- 为了让系统答对而改写的提示词、检索词或补充事实。

运行前记录：

```yaml
system_inputs:
  question: "<与案例问题逐字一致>"
  question_sha256: "<UTF-8 字节的 SHA-256>"
  identity_confirmation: null
  reference_used: false
```

### 8.2 运行记录

| 字段 | 要求 |
|---|---|
| `investigation_id` | API 返回的真实 UUID |
| `submitted_at` | 提交时间 |
| `terminal_status` | `SUCCEEDED`／`FAILED`／`CANCELLED` 等真实状态 |
| `stage` | 真实阶段 |
| `error` | 失败时记录 code／message／retryable；不得改写 |
| `snapshot_id` | 成功时的真实快照 UUID；失败为 `null` |
| `snapshot_version` | 快照版本号 |
| `snapshot_generated_at` | 快照生成时间 |
| `contract_version` | 读取到的契约版本 |
| `identity_result` | 系统解析出的产品身份；与人工身份的差异 |
| `retrieval_records` | 系统真实检索记录；没有则说明 |
| `answer_summary` | 系统回答摘要；不替代原文 |

规则：

- 未配置提供方时，Worker 失败是正确行为；记录 `PROVIDER_NOT_CONFIGURED`，不能手工改数据库或伪造成功。
- 不直接插数据库绕过 Zod 和事务发布；系统运行只走正式 API／Worker。
- 失败也要记录调查 ID、错误和尝试时间；不能把失败写成“系统未找到相关信息”。
- 历史快照要标版本和生成时间，不能称为“本次最新成功”。

### 8.3 对照

对照按 `Q-ID` 和 `C-ID` 逐条进行，不按整段文字感觉判断。

| 对照结论 | 含义 |
|---|---|
| `一致` | 答案、范围、条件一致 |
| `部分一致` | 核心答案相同，但范围／条件／时间有差异 |
| `冲突` | 答案方向不同，或一方支持一方反驳 |
| `系统缺失` | 系统没有回答该问题，或没有可核对内容 |
| `不可比` | 问题、身份、版本、地区不同，运行无效 |
| `系统错误` | 系统运行失败，没有可评估结果 |

引用对照还要检查：marker 是否在正文、证据 ID 是否存在、原句是否逐字符匹配、原句是否真的支持该句、是否把官方宣称当独立事实、是否漏掉冲突和缺口。

对照时不预设“人工一定对”。如果系统结论与参考不同，回到原文判断；若参考错了，修正参考并在变更记录说明，不能为了维持人工权威而改系统。

## 9. 独立复核

- 复核人按交接要求为丙；如由其他人替代，记录原因和核心是否同意。
- 顺序：先只看问题与原始材料，写独立判读；再读 `reference.md`；最后看系统结果与对照。先看结论再“复核”不算独立。
- `review.md` 必填：复核人、时间、收到的材料、逐问独立判断、与参考判断的同意／分歧及依据、系统结果复核、阻断性错误检查、最终意见。
- 分歧不强行统一；不能解释的列入缺口或阻断项，保留双方意见。
- 没有复核人签署，不得标“已独立复核”。

## 10. 状态与交付门槛

状态分三维：材料、系统、复核。定义见 [入口与索引](README.md#3-状态模型)。

| 门槛 | 条件 |
|---|---|
| 材料可用 | 六项齐全；参考判断通过适用标准（G1–G12 中适用项）；无阻断性错误；乙已确认 |
| 系统对照完成 | 有真实运行记录；成功时有快照；逐问对照完成；失败也记录 |
| D1 交接完成 | 三案材料可用；至少一案有海外原句与真实冲突（或明确报告未完成）；丙已独立复核 |
| 最终通过 | 被评估对象无阻断性错误，适用标准全部通过 |

系统失败不自动使案例材料不合格；但它使“系统对照完成”无法成立，评估结论应写“无法评估”或“系统失败”，不能写“通过”。

## 11. 红线与禁止事项

- 不碰时政；不调查具体个人的私人身份、联系方式、私德；只保留必要的公开作者名／账号与公开角色线索。
- 引用三件套：原句 + URL + 获取日期，缺一不可；每条 ≤300 字符，只摘关键句。
- 官方宣称与第三方实测分栏；官方 benchmark 不当作独立实测；转载不当作独立来源。
- 读取失败 ≠ 没有讨论；失败写真实原因，未知写未知。
- 负面措辞有范围：写“在已查范围内未找到支持该说法的公开来源”或“该说法与当前官方文档不一致”，不写“虚假宣传”“骗子”“割韭菜”。
- 不使用虚构证据、虚构作者、虚构时间、虚构人工判断或虚构复核。
- 不把 `tests/fixtures`、历史占位案例、附录 A 虚构样例当作 D1。
- 不把人工参考判断送入系统；不以参考结论反向填充系统输出。
- 不为了凑“三案齐”而缩短范围、隐藏冲突或把失败写成成功。

## 12. 文件与字段映射

每个案例目录包含三个文件：

| 文件 | 内容 | 谁能读 |
|---|---|---|
| `case.md` | 问题、身份、时间、范围、检索、证据、主张、冲突、缺口、系统运行 | 人、材料整理工具；系统运行时不得读取 |
| `reference.md` | 人工参考判断、确认、系统对照、评估结论 | 人、离线评估；**禁止系统运行时读取** |
| `review.md` | 丙的独立复核 | 人；复核完成后供交付 |

六项材料要求与模板章节的对应关系见 [交接要求对照](D1-交接要求对照.md#2-六项材料要求逐项对照)。
