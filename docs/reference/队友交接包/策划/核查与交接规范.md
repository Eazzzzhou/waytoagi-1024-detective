# 案卷｜核查与交接规范

版本：v2.2 · 2026-10-24。这里只约定影响可信度和共同理解的关键事项。交付数量与验收见[任务派单](迭代与任务派单.md)；研究方法、工具、工作顺序和展示方案由负责人自行设计。

## 产品共识

用户只想查产品时，直接给有出处的客观搜索结果；用户需要适配建议时，再结合他的要求判断。两者共用查证链路。

元宝在核心检索和补查中有实际作用；海外社区是重要信息来源，相关平台和论坛按问题拓展。队友的核查成果服务核心验证和展示，并不需要实现抓取与算法。

## 红线（任何交付都不得越过）

1. **不碰时政**；不调查具体个人的私人身份、联系方式与私德。证据归属只保留必要的公开作者名／账号与公开角色线索，不延伸做个人画像。
2. **引用三件套**：原句 + URL + 获取日期，缺一不可；仅摘关键句，超过 300 字不整段转载，改为关键句加链接。300 字是本包摘录约束，不代表版权免责。
3. **负面措辞有范围**：写“在已查范围内未找到支持该说法的公开来源”或“该说法与当前官方文档不一致”，不写“虚假宣传／骗子／割韭菜”。
4. **官方宣称与第三方实测必须分栏**；官方 benchmark 不当作独立实测，转载不当作独立来源。
5. **读取失败 ≠ 没有讨论**：如实写“读取失败（403／超时／无权限等实际原因）”，不得改写为“没有相关信息”。原因不明就写未知，不猜测错误码。

## 五项共同要求

### 1. 依据能够找到

关键结论有原始出处，引用能够定位。必要的时间、产品版本或套餐条件有记录；无法确认的内容如实标明。搜索摘要、译文和系统归纳按其实际性质表达。

### 2. 判断能够解释

分清可检验事实、官方宣称、使用者观点和自己的归纳。核查结果能说明依据与局限；不同模型意见一致不自动等于事实已被验证。

### 3. 分歧和未知能够看见

有价值的反例与冲突保留，能解释的说明条件，不能解释的保留疑问。原文未取得、来源访问失败和确实没有找到材料应当可区分。

### 4. 独立性有依据

跨平台不自动等于独立来源。同一作者跨发、转载或共用上游测试应当能识别；无法确认时说明不确定。具体分组和判定方法可在真实案例中探索。

### 5. 展示忠于材料

用户能分清原话、译文和归纳；能知道观点的归属和适用范围。热度可作背景，不代替证据。一般搜索结果不会因为推荐条件或推荐证据不足而被遮住。

## 交付需要带上什么

每个案例**必填 6 项**，其余按实际需要补充：

1. 案例 ID（`A-01` 起）与产品、版本／套餐。
2. 用户问题原话 + 回答意图（客观搜查／适配建议）。
3. 证据列表：URL、原句、站点、发布时间、作者或公开身份线索；每条附获取日期，可统一声明同批获取时间。未知元数据写“未知”，读取失败则保留 URL 与真实状态，不补造原句。
4. 每条证据支持／反驳／无关于哪个主张；不能判断也要说明。同源关系一并注明，不重复当独立支持。
5. 冲突与缺口：区分未取得、读取失败、已在明确范围内检索但未找到。有限检索不能断言整个互联网“确实没有”。
6. 核查时间与核查人；独立复核在案例末尾另记人、时间、判断与依据。

**明确不要求**：错误分类体系、置信度百分比、评分表。表达形式自选，D1 按任务派单用 Markdown 交接；六项是材料要求，不是技术数据结构。参考[附录 A](附录A-案例样例.md)。

展示口径参考[附录 B](附录B-口径样例.md)，需另配两份真实示例。反馈系统问题时附可重现输入、实际结果与原文依据，不要求错误分类。

## 可以自主决定的事项

在核心提供的候选范围与派单交付数量内，具体问题、来源组合、工具、采集和核查方法、标注形式、文案、页面布局以及工作顺序由执行者自行计划。可以用模型协助，但核查结论应能回到材料独立说明。

核心算法、推荐规则和技术数据结构由你主导迭代，队友以样本和发现提供建议。原画像中的八维、四档和推荐门槛保留为当前参考；它们不应被套到所有客观搜索上，也不要求核查团队先实现一套评分系统。

## 什么时候需要对齐

只有影响产品方向、共同判断含义、其他人的交接或实际资源需求的变化，才需要及时对齐。其他选择可直接执行，并在交付时说明。

验证中发现旧口径不合适，可以带着案例提出更好的方案。规范随产品迭代，目的是让成果接得上、依据讲得清。
