# PostgreSQL 可靠异步任务 · 第二阶段

本文描述已实现的数据库队列和独立 Worker；HTTP 与最小前端已接通，但甲的搜索、核查和回答算法尚未接入。正式入口 `src/server/investigation/handler.ts` 仍明确抛出不可重试的 PROVIDER_NOT_CONFIGURED。测试处理器只存在于测试目录，不与正式入口关联。

第三阶段补充：HTTP 和最小前端已接通，见 [HTTP接口与错误码说明](HTTP接口与错误码说明.md)。第二阶段的领取、续租、过期回收、执行令牌和事务发布逻辑保留；仅增加以下用户控制接口：

- `confirmIdentity(..., {requireWaiting:true, expectedAttemptCount})` 在同一 Job 行锁事务中严格检查等待状态和当前尝试；HTTP 重复确认返回冲突，原服务方法的幂等回执语义保留。
- `retryFailed(investigationId, {expectedAttemptCount})` 仅允许可重试的 FAILED 任务，每项调查最多两次手动操作。每次 maxAttempts 加 1，不清零 attemptCount/failureCount、不删除历史尝试，清除旧令牌后交回原领取机制。
- 新增内部字段 manualRetryCount 与数据库 0–2 CHECK；不改变证据快照契约。终态不会被普通 Worker 自动复活，只有符合规则的显式用户操作能恢复执行。

## 启动与提交

```powershell
npm run db:up
npm run db:migrate
npm run db:test:migrate
npm run worker
```

Worker 持续运行直到 Ctrl+C / SIGINT / SIGTERM；空闲时轮询，不输出模拟进度。另一个终端可提交一个真实问题：

```powershell
npm run investigation:enqueue -- --key my-first-question --question "这个 AI 产品的免费版支持导出吗？"
```

该命令创建真实调查和任务，不生成结果。未接入业务编排时，Worker 会将其标为 FAILED，保存 `PROVIDER_NOT_CONFIGURED`，快照与回答为空。重复运行相同 key 和同一问题返回原调查；不同问题报 `IDEMPOTENCY_CONFLICT`，退出码 1。配置完成后如需重新调查，使用新的请求键；旧键保留原失败记录，不自动复活终态任务。不要把测试问题提交到正式数据库。

项目 `.env` 中的 DATABASE_URL 仅供服务端使用。默认参数都在 `.env.example`；已有 `.env` 无需覆盖，未设置的 Worker 选项使用默认值。

## 队列接口

入口 `PostgresInvestigationQueue` 接收 PrismaClient 和经过 Zod 验证的配置。Web 将来可以调用服务方法，但不能启动或导入 Worker 入口。

| 方法 | 行为 |
|---|---|
| `enqueue({question, idempotencyKey})` | 一个短事务内创建 Investigation 和 Job；返回 investigation、jobId、reused |
| `claim(workerId)` | 领取一项到期 PENDING 任务，返回 ExecutionLease 或 null；不自动回收过期任务 |
| `loadTask(lease)` | 验证有效归属并读取问题与已确认身份；重新校验 JSONB |
| `heartbeat(lease)` | 数据库时间续租，返回更新的 expiresAt；不能越过单次执行截止时间 |
| `advanceStage(lease, stage)` | 保存当前真实阶段到 Investigation 和本次 ExecutionAttempt；不能直接设置 COMPLETED |
| `complete(lease, {snapshot, answer})` | 同一事务内校验、写快照／回答、完成任务；相同结果重放返回 reused |
| `fail(lease, error)` | 保存具体错误，按 retryable 与失败预算转为 PENDING 或 FAILED |
| `awaitConfirmation(lease, {identity, reason})` | 持久化身份确认请求，任务和调查转入 AWAITING_CONFIRMATION，本次尝试结束 |
| `confirmIdentity(investigationId, identity)` | 仅显式调用并通过 CONFIRMED 身份契约后恢复 PENDING；相同确认内容可幂等重放 |
| `recoverExpired()` | 有界批量回收过期执行，记录 LEASE_EXPIRED 尝试和错误，重试或进入终态 |

原第一阶段的 queue interface 是未使用的草案，第二阶段将入队入口落实为原子创建调查和任务，避免调用方先建调查再入队产生孤儿记录。本阶段一项调查只有一个 Job，由唯一约束保证；补查与多任务类型尚未建设。

ExecutionLease 包含 `jobId, investigationId, attemptId, executionToken, workerId, expiresAt`。expiresAt 是观测信息，**不用于客户端判断归属**；数据库中的当前 token、owner、尝试 ID、状态、到期时间才是依据。请勿对外暴露租约或令牌。

## 幂等与事务

入队时对标准化幂等键取 PostgreSQL 事务级 advisory lock，然后查找已有 Job。问题仅去除首尾空白，其余内容保持原样；`question:v1:` 加标准化问题的 SHA-256 存为 requestHash。相同键／hash 返回原调查；不同 hash 返回冲突。锁哈希碰撞只会多串行等待，不会错误复用请求。唯一 idempotencyKey 和唯一 investigationId 是数据库的最终约束。

领取按 availableAt、createdAt、id 排序，使用 `FOR UPDATE OF j SKIP LOCKED`。同一事务内更新 Job、创建 ExecutionAttempt、更新 Investigation，提交后才调用 handler。每次领取都会生成新的随机 executionToken，attemptNumber 单调增加。过期和重试均创建新尝试，不覆盖历史尝试。

所有归属更新先锁 Job，并核对其当前 token、workerId 和对应的尝试 ID。锁后用 **clock_timestamp()** 重新检查有效期，避免使用事务开始时冻结的 now()，也避免把等待行锁的时间排除在租约之外。心跳不能复活已过期的租约；即使尚未被回收，旧 Worker 也不能续租、更新阶段或完成。

最终发布事务会：

1. 锁 Job 并验证当前归属与有效期。
2. Zod 校验快照、回答和引用关系，然后写入快照与回答。
3. 更新 Investigation、ExecutionAttempt 的完成状态。
4. 最后执行带 token、RUNNING、租约和执行截止时间条件的 Job UPDATE；未命中则整个事务回滚。

Job.completionHash 保存经 Schema 解析后的结果摘要，publishedSnapshotId 唯一关联已发布快照。相同当前执行的完成请求重放仅返回完成回执，不新增快照；同一执行提交不同结果报冲突。已成功的相同 token／相同摘要重放可以在租约结束后读取回执，这是只读幂等回放，不授予新的写权限。更旧的 token 一律被拒绝。

快照 `(investigationId, version)`、快照 ID、回答 ID 和 publishedSnapshotId 的唯一约束进一步防止重复发布。响应丢失时，应重放同一组 ID 和相同结果内容；不要重新生成 ID 再提交。业务 handler 不直接持久化最终结果，只把校验后的对象返回给 Worker。

所有队列事务只做数据库操作，事务超时 5 秒、等待连接上限 5 秒、行锁等待上限 2 秒、单条 SQL 上限 4 秒。事务中不得调用外部 API。事务期间截止时间到期，发布仍会回滚；最终带条件写入是提交归属的判断点。

## 恢复、退避与错误

Worker 每轮先回收过期任务，再领取一项任务。每次回收最多 20 项，每项独立短事务，多个回收者同样使用 SKIP LOCKED。回收不会猜测外部 API 是否执行过，只标记旧尝试为 LEASE_EXPIRED，并保存具体的 LEASE_EXPIRED 或 TASK_TIMEOUT 错误。

Job.failureCount 计算失败次数，包括主动失败、执行超时、崩溃导致租约过期和主动关闭中断；maxAttempts 是整个 Job 的失败预算，创建时持久化。普通无确认流程最多执行 maxAttempts 次失败尝试。等待身份确认不消耗失败预算，所以 attemptCount 在显式确认后可以大于 maxAttempts，但失败次数仍有上限。重试不会清零失败预算。

可重试错误在未耗尽预算时转为 PENDING；availableAt 使用数据库时间加 `min(retryMaxMs, retryBaseMs × 2^(failureCount−1))`，到期前不可领取。第一版使用确定性指数退避，不加随机抖动。不可重试错误或预算耗尽立即 FAILED。错误同时保存在 Job.lastError、ExecutionAttempt.error、Investigation.error；重试领取会清除调查当前错误，Job 仍保留最近历史失败，成功后清除 Job.lastError。

| 错误 | 默认处理 |
|---|---|
| PROVIDER_NOT_CONFIGURED / CAPABILITY_NOT_IMPLEMENTED | 不可重试；配置／实现补齐前不要反复调用 |
| PROVIDER_FAILED | 甲必须明确 retryable，例如 429、暂时网络错误可重试，认证错误不可重试 |
| INVALID_INPUT | Zod 拒绝输入或 handler 输出，不可重试 |
| TASK_TIMEOUT / LEASE_EXPIRED / WORKER_SHUTDOWN | 可重试，受失败预算限制 |
| STORAGE_FAILED | 已识别断线、连接池超时、序列化失败、死锁或锁超时可重试；唯一约束等错误不可重试 |
| LEASE_LOST | 当前 Worker 停止写入；由回收者决定后续状态 |
| IDEMPOTENCY_CONFLICT | 不可重试原请求，需要调用方处理冲突 |
| UNKNOWN | 保存具体错误理由，保守地不自动重试，避免无限重复未知副作用 |

甲可抛出 `new TaskFailure({code, message, retryable})`；message 必须具体且已脱敏。框架对常见凭据格式和服务端密钥环境变量再做脱敏，日志不输出完整异常栈、问题正文、证据正文或数据库连接字符串。数据库当前不可达时，不能保证把本次错误立刻写回；Worker 记录结构化日志、停止本次处理并重试轮询。未成功提交的状态保留在数据库，恢复连通后按数据库租约回收。

## 身份确认

确认请求中的 identity 必须为 NEEDS_CONFIRMATION，并持久化 reason。Job 与 Investigation 都为 AWAITING_CONFIRMATION；领取和回收 SQL 都不会把该状态当作待执行任务。

`confirmIdentity` 必须由未来经过用户操作的服务入口显式调用；它要求身份为 CONFIRMED，并符合官网与确认依据等现有契约，才恢复同一个 Job。新执行将获得新 token，handler 的 confirmedIdentity 传入已验证对象。不会因为超时、Worker 重启或普通轮询自动替用户确认。本阶段没有确认页面或 HTTP 路由。

## Worker 与甲的接入契约

`InvestigationHandler(context): Promise<HandlerResult>` 在 `src/server/investigation/handler.ts` 定义。context 提供：

- investigationId、question、可空 confirmedIdentity。
- AbortSignal，用于超时、关闭或续租失败时停止外部请求。
- `setStage(stage)`，只在真实阶段发生时调用；它自动校验租约并保存调查与尝试的阶段，不接受模拟进度。

返回值只能是：

```ts
  { kind: "COMPLETE", result: { snapshot, answer } }
// 或
{ kind: "AWAITING_CONFIRMATION", request: { identity, reason } }
```

失败通过 TaskFailure / CapabilityError 抛出。所有 provider 原始响应与模型输出仍须在甲的实现内部做 Zod 校验；Worker 还会验证 handler 最终输出。快照所属调查、回答所属快照和引用关系必须一致。不要返回空成功来绕过未配置服务；正式入口目前只有明确的不可用失败。

Worker 每次只执行一个 handler；心跳串行续租，不重叠累积。单次执行有数据库硬截止时间，心跳最长续到该截止点。Node 超时或丢失心跳时发出取消信号，忽略迟到结果；即使第三方 SDK 不响应取消，迟到结果也不能经本 Runner 发布。

收到 SIGINT/SIGTERM 后停止领取，取消当前 handler，并尝试记录可重试中断，然后断开数据库。若数据库不可达或 provider 忽略取消而占用进程，关闭宽限到期后强制退出，留下租约供后续恢复。Windows Ctrl+C 可触发 SIGINT；强制结束进程走租约回收路径。

**外部 API 是至少可能重复调用的。** 崩溃、网络异常和无法确认响应时都可能再次调用；本实现保证队列归属与数据库发布的幂等约束，不承诺外部 API 严格执行一次。甲需要把 AbortSignal 传入 HTTP/模型请求，并在提供方支持时使用其幂等键。不要在 handler 中直接改 Job、调用无令牌的快照写入或自行提交成功状态。

## 配置

| 环境变量 | 默认值 | 含义 |
|---|---:|---|
| WORKER_POLL_MS | 1000 | 空闲／数据库错误后的轮询间隔 |
| WORKER_LEASE_MS | 30000 | 每次租约长度 |
| WORKER_HEARTBEAT_MS | 10000 | 心跳间隔，必须小于租约和单次超时较小值的一半 |
| WORKER_TIMEOUT_MS | 300000 | 每次领取后单次执行硬截止时间 |
| WORKER_MAX_ATTEMPTS | 3 | 入队时写入新 Job 的失败预算；修改不会改变已入队任务 |
| WORKER_RETRY_BASE_MS / WORKER_RETRY_MAX_MS | 1000 / 60000 | 指数退避基数／上限 |
| WORKER_SHUTDOWN_GRACE_MS | 10000 | 进程关闭宽限 |

Worker ID 由主机名、PID 和随机 UUID 生成，不作为用户身份或权限系统。配置只影响本进程新领取的租约与退避，建议所有 Worker 使用相同配置。数据库是唯一的归属和时间权威，不依赖机器时钟同步判断租约。
