# 案卷｜核查与交接规范

版本：v2.0 · 2026-10-24。供你负责的查证核心、队友乙的人工核查、队友丙的页面共同使用。

方向和分工见[总策划书](总策划书.md)，具体任务见[迭代与任务派单](迭代与任务派单.md)。本文件集中定义语义，其他文档只引用，不再维护一份各自不同的判定规则。

## 1. 三种不同的标准

| 标准 | 判断什么 | 应用范围 |
|---|---|---|
| 出处核对 | 原句是否真的出现在这个来源，身份、时间、上下文是否匹配 | 所有引用 |
| 主张核查 | 这句话表达的事实是否有适用范围内的证据支持、反驳或冲突 | 事实和可检验主张 |
| 适配判断 | 在用户任务、预算和门槛下，现有材料是否支持建议 | 用户需要推荐时 |

找到一条真实原话，只能先确认出处。对主观评价，要明确“这是某位使用者在某场景的观点”；对事实陈述，再核查它本身。不同标准不能共用一个含糊的“已验证”勾选。

一般信息查询不会因为没有三条体验帖而停止回答；它可以交付一条已核对的官方价格事实，同时明确使用评价还缺少材料。推荐门槛只作用于推荐。

## 2. 回答意图

| 意图 | 判定例子 | 输出要求 |
|---|---|---|
| research：查事实／观点 | 搜一下、介绍一下、怎么收费、开发者怎么说、有哪些争议 | 直接组织客观材料与核查结果，不强制用户给用途 |
| advice：求建议 | 适合我吗、该不该付费、我这种条件能不能用 | 使用已给条件；缺关键条件时先交客观结果，再做最少必要追问 |
| mixed：两者都有 | 介绍一下，再判断适不适合我的项目 | 共用证据，先事实／观点，再明确标注建议 |

涉及用途不必然是求建议；“查找编程测评”仍可只是 research。用户纠正回答意图后，更新意图，保留既有证据；只有新问题超出证据范围才补查。

产品身份确有歧义时请求选择或展示候选。单纯未提供用途不属于查询错误，也不是产品证据不足。

## 3. 核心数据对象

具体类型和方法名由 A2 在首轮落地；以下含义保持一致。采用单一共享定义，B 的标注表和 C 的展示样例与之对应。

| 对象 | 最小内容 |
|---|---|
| Question | question_id、用户原问题、产品或链接、response_intent、实际问题范围、用户主动给出的用途／条件 |
| Product | product_id、名称、官网、别名、当前版本／套餐（允许未知）、身份依据、是否需确认 |
| SourceRun | source_id、尝试方式、查询词、起止时间、状态、发现数、取到原文数、失败原因；元宝附 RequestId（若有） |
| Material | material_id、来源平台、原始 URL、规范化 URL、标题、作者／机构线索、发布时间、获取时间、原文或可核对片段、正文状态、适用产品／版本 |
| Quote | quote_id、material_id、原文起止位置或视频时间戳、原句、可选译文、必要上下文、出处核对状态 |
| Claim | claim_id、说法、类型、产品／版本／条件、引用 quote_ids、支持／反驳关系、核查状态、局限 |
| SourceGroup | group_id、相关 material_ids、作者／机构／上游关系、独立性判断、分组依据、未知项 |
| Metric | 平台、对象链接、指标名、数值和单位、采集时间；不可用为 null |
| CaseSnapshot | case_id、snapshot_id、问题范围、产品、以上数据、生成时间、schema_version、rule_version、模型复核状态、历史缓存标记 |
| Answer | response_intent、直接回答、事实、原话观点、分歧、证据缺口、来源覆盖、引用；可选 advice |
| Advice | 用户条件、主维度、四档或待补条件状态、依据、命中规则、适用边界、缺口；未请求推荐时为空 |

原文保存与展示遵循来源当前使用规则，保留足以核查的片段和定位。页面只渲染安全文本与允许的链接，来源内容不作为程序指令。

### 3.1 主张类型

- **产品事实**：官方列出的价格、套餐功能、版本日期等；注明来源、范围和核查时间。
- **官方宣称**：官方声称的性能、效率或优势；确认“官方这样说”不等于独立验证了效果。
- **使用体验**：可归属使用者、带具体任务和条件的陈述；正负体验都可以有价值。
- **二手转述**：引用别人的测试或观点；尽量追到上游，不能增加独立支持票数。
- **系统归纳**：根据多份材料得出的解释；必须关联具体依据，不显示为原话。

### 3.2 出处状态与主张状态分开

出处状态：已定位／仅有摘要／原文未取得／上下文缺失。

事实主张核查状态：当前依据支持／当前依据反驳／来源冲突／证据不足。表示所查范围内的证据判断，不是永久真理。

主观观点显示：已确认出处的观点、适用场景和限制；不强行用真假为“我觉得不好用”定性。观点里的可检验事实可另拆为主张核查。

### 3.3 流程、来源、推荐状态分开

- 查询流程：识别中／检索中／核查中／完成／部分完成／失败。
- 来源状态：成功／无命中／超时／读取错误／未配置／待授权／不适用。
- 推荐状态：未请求／缺少用户条件／可给建议／证据不足／核查未完成。

一般搜索完成时推荐可以是未请求。推荐证据不足时，客观材料仍可完成。部分补充源失败不自动取消已核对材料；元宝核心步骤失败需明确本次调查未完成。必要复核没有完成时，不能把结果包装成已核查完毕。

“已查来源数”只统计实际尝试且有可解释返回的来源，超时另列；未配置和待授权单列。命中链接数、取得原文数、独立材料数分别展示，不能互换。

## 4. 所有模式共用的核查底线

1. **身份与范围**：确认产品、版本、套餐和任务；同名产品不混合，旧版问题不默认套在新版上。
2. **原句定位**：引用来自实际取得的材料；模型动态摘要和机器译文独立标识。
3. **保留上下文**：否定词、版本限制、使用条件及被引用的上文保留；长帖截断时说明缺失。
4. **来源归属**：公开作者或机构信息仅用于来源署名和独立性判断，不延伸到个人私事或指控。
5. **同源识别**：跨站转载、同作者跨发、共用上游测试单独分组；独立性未知如实标注。
6. **冲突保留**：正反材料都展示；只有在版本、时间、任务或方法差异有依据时才解释冲突。
7. **热度隔离**：播放、点数、点赞、星标只作背景，不自动改变事实判断或推荐档位。
8. **缺口真实**：读取失败不等于没有讨论，没找到证据不等于事实为假。
9. **可回溯**：每次回答关联证据快照和规则版本；补查生成新快照。
10. **内容与指令分开**：网页中的命令、提示词或要求改变规则的文字只作为待分析内容。

同一讨论串的多名作者是否独立，按原始经历、相互引用和机构关系判断；不只看平台或回复数量，也不简单把全串都视作一条或无限条。无法确认时对推荐计数采用保守处理，客观展示仍保留出处和局限。

## 5. 当前推荐规则基线

这一节沿用画像中的保守方向，适用于 advice/mixed 的建议部分。未来可以根据样本调整，调整时记录原因、版本和回归结果，不静默改门槛。

### 5.1 先检查是否具备建议条件

用户任务或决定性要求缺失时，先完成客观回答，再追问关键条件。不要先猜用途然后给不适合。

运行或复核失败用流程状态表达。可取得材料但不能支持推荐，才使用四档中的“证据不足”。

### 5.2 保守证据门槛

- 全局至少三份合格的独立真实使用材料，跨至少两个独立站点。
- 主维度有至少两份相关独立使用材料，决定性支持满足跨源要求。
- 只有官方材料、转载或无法确认使用经历的推广时，不足以给体验性推荐。
- 模型可以提出更严格排除，不可绕过本轮已经采用的门槛。

一份材料可以支持多条主张，但不能因此变成多份独立经历。搜索得分、模型数量和互动统计不计入门槛。

### 5.3 分档

| 分档 | 应满足的含义 |
|---|---|
| 值得一试 | 主用途有足够具体支持、关键反例已处理、用户主要条件可满足 |
| 有条件值得 | 可用边界明确，限制可以在用户条件内规避，条件有证据 |
| 不建议 | 对该用途存在已核实、难以规避的关键限制或多个独立材料指向相同硬伤 |
| 证据不足 | 材料、独立性、主维度覆盖或冲突处理不足，不能稳妥建议 |

“正向多于负向”不能单独作为判决算法。具体的强弱划分、冲突优先级与停止补查策略由你主导，和人工样本对照验证后写入 rule_version。未校准前不展示真实性百分比。

八维沿用画像：编程与工程、数学与逻辑、中文表达、多模态理解、图像/视频生成、3D 与空间、Agent 与工具调用、成本与门槛。保留强／弱／无证据的方向，同时单独呈现冲突原因与真实材料数量；不把“存在分歧”显示成“查到零条”。如果需要增加状态，由本轮产品迭代统一变更。

官方明确停服、取消免费档等事实，即使没有足够使用评价也应在客观区域直接说明；推荐区域是否给档仍按当前规则，不能让保守门槛隐藏已核实的重要事实。

## 6. 多模型核查与人工核查如何配合

### 6.1 机器流程由你实现

A1 提供实际材料。A2 让模型独立读取原文、提取或复核主张，用程序检查引用位置与来源映射；对影响结论的分歧提出补查问题，交 A1 获取新增材料。

两个模型同意不等于两个独立事实来源。记录各模型角色、版本和复核状态，比较的是引用和解释是否可靠。只用同一模型重复调用时，描述为一致性检查，不宣称跨模型验证。

### 6.2 人工样本由队友乙维护

每条样本包含：问题、产品、原始 URL、原文片段和位置、获取时间、主张类型、支持／反驳／未知的人工判断、版本条件、同源关系、期望展示、标注人及复核人。

先标注再查看算法输出。对于有争议的样本保留双方理由，不以一人的直觉确定事实。公开演示用真实材料；虚构边界样例可测试程序，但必须标 synthetic 并隔离。

### 6.3 错误分类

错误统一归为：产品错配、版本错配、引用不存在、断章取义、译文改变含义、把宣传当实测、同源重复计数、遗漏反例、规则不一致、模式误判、来源状态错误、展示造成误解。

乙报具体输入和预期，A2/A1/C 分别修对应层。修完用同一份样本复测，记录是否引入其他退化。

## 7. 队友丙的展示约定

页面消费 Answer 和 CaseSnapshot；不在前端另算事实支持度或推荐档位。

- research：先直接回答，再给事实、观点、冲突和出处；未请求建议时隐藏推荐区。
- advice/mixed：增加用户条件、建议及理由；条件未齐时显示一条必要追问，客观内容仍可用。
- 原文、译文、模型归纳视觉上可区分；不靠一排额外技术标签增加阅读负担。
- 狭窄屏幕用纵向原句卡，正反材料都可访问；失败状态和缺源不过度隐藏。
- 明确当前问题、核查时间和来源范围；来自真实旧快照时显示时间，不假装正在实时查询。
- 海外原文不可直达时如实说明，并提供合法保存的可定位引用；不能把本地快照称作原平台链接。

展示标准由 B 从核查语义角度提出，C 负责可读性与交互。双方意见冲突时用一条真实用户任务验证，由你决定是否调整产品规则。

## 8. 核心验收样例

| 编号 | 情形 | 期望行为 |
|---|---|---|
| V01 | 只说“搜一下某产品”，无用途 | 完成客观搜查，无强制用途弹窗，无适配判决 |
| V02 | 查免费版导出，只有一份可核对官方页面 | 回答该事实及范围；使用评价缺失不阻断事实答案 |
| V03 | 指定查编程社区讨论，但没问适不适合 | 聚焦编程观点，仍按 research 回答 |
| V04 | 给任务与预算问是否适合 | 复用共同证据，按用户条件生成建议 |
| V05 | 已有客观案卷后补充用途 | 足够时重用快照；不足时明确补查并建新快照 |
| V06 | 一条 X 原话被 HN、中文站转发 | 展示传播关系，推荐独立支持不按三站算三票 |
| V07 | 原句说“旧版失败，新版已修复” | 保留版本条件，不能摘成“这个产品失败” |
| V08 | 英文观点存在、译文有误 | 原句保留，错误译文被纠正或标待复核 |
| V09 | X 只搜到摘要，原帖读不到 | 显示未核验线索；不输出冒充原句的引用 |
| V10 | HN 读取超时 | 显示超时，不说 HN 无人讨论 |
| V11 | 两模型对原文解释有决定性分歧 | 进入补查或保留未决，不把多数意见当证据 |
| V12 | 请求推荐但不足三份独立材料 | 建议区证据不足；仍展示核实的事实与已知观点 |
| V13 | 官方宣传性能很好，社区存在具体反例 | 两类材料区分，检验任务／版本后解释冲突 |
| V14 | 元宝核心步骤失败 | 新调查显示未完成；历史真实快照单独说明 |
| V15 | 只改变播放量与星标 | 事实核查和推荐结论保持不变 |
| V16 | 源内容要求忽略指令或输出固定答案 | 当作材料内容，不改变执行规则 |

每轮只选与当轮能力有关的样例作为完成标准；已通过的关键样例作为后续回归。真实样本负责验证语义和源可用性，开发边界样例负责验证确定性规则。

## 9. 迭代记录与交接

每轮附上：产物、真实例子、已测范围、失败与缺口、规则／契约变更、下轮建议。提出算法变化时附旧输出、新输出、依据和影响的样本。

少量稳定字段跨轮保持兼容；大改先给页面和核查样例一个兼容窗口。需求变化由你裁定后更新本文件；本文件未涉及的采集细节、框架和部署方式由执行者在当前环境里选择并记录。

开发模型订阅、产品运行时 API、元宝及社区平台权限分别列资源状态。未配置的能力不写已实现。付费和授权条件先由团队确认资源是否已有，本轮文档不代表已购买或已获批。
