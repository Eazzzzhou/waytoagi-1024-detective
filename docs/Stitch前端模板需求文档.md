# 案卷：前端产品需求与 Stitch 模板设计说明

版本：1.0 · 2026-10-25。用途：交给 Stitch 生成可落地的前端视觉模板与状态页面，不要求 Stitch 实现搜索、数据库或完整业务后端。本文件是设计需求，现有功能边界以当前工程共享契约与接口为准。

## 1. 产品定义

产品名称：**案卷**。副描述：**AI 产品调查与证据核查**。

这是围绕具体 AI 产品问题进行网络调查的研究工具。用户提出问题后，系统异步解析产品身份、检索材料、读取来源原文、核查主张并整理客观回答。用户既能直接阅读回答，也能沿引用追溯原文、理解冲突和证据局限。

设计应使三个问题一目了然：“我在查什么？”“调查现在怎样？”“结论凭什么成立？”

目标用户：普通用户，希望迅速理解产品信息及可信程度；严谨用户，希望核对每条主张、原句和来源关系。主界面为简体中文，允许英文产品名称、原文、长 URL 和技术标识混排。

## 2. 本轮设计目标与范围

优化现有 Web 产品的视觉层级、提问入口、状态反馈和证据阅读体验。首要目标是让用户准确理解证据，不以装饰或内容填充制造可信感。

本轮只包含两个真实路由：首页 `/`、调查详情 `/investigations/:id`。不同运行状态是详情页变体，不是新的导航模块。

不设计为可用功能：调查列表／最近调查、收藏、团队、个人中心、登录注册、订阅付费、数据仪表盘、补查、追问、自动建议 Advice、取消任务、下载／分享／复制操作、执行历史列表与版本切换。这些当前没有完整支持，不要添加相应菜单、按钮或占位入口。需要版本信息和历史结果提示，但不虚构历史浏览能力。

## 3. 现状与设计内容真实性

前端和公共异步工程已实现；真实搜索／核查提供方仍待接入，当前正式执行可能返回 PROVIDER_NOT_CONFIGURED。失败页面是必要设计场景。

已有三个真实 D1 材料草稿，但系统执行记录仍为 NOT_RUN，尚无对应正式成功快照。不要将案例草稿排成“真实调查成功案例”，不要声称产品已完成调查验证。

Stitch 可以为成功页使用**明确标注的隔离设计样例**，其用途只为展示结构与长内容密度。页面须保留“设计样例／非正式调查结果”标识，所有虚构文字不可作为正式数据回写。不要编造权威引语、真实来源链接、作者、媒体背书、置信度、准确率、用户数量或调用量。无原文时显示缺失状态，不生成替代原句。真正上线内容由接口提供。

## 4. 视觉方向

关键词：现代、精致、可信、明亮、克制、有辨识度的专业研究工具。信息密度高但不拥挤。

以“案卷阅读”为构图核心：问题是案卷标题，回答是主体，引用是正文与证据之间的连接，限制与冲突是结论的组成部分。首页集中提问；详情正文优先，证据目录辅助定位。连续阅读面应有清晰排版节奏，不是所有信息放进相同圆角卡片。

已有用户验收基线：顶部案卷栏＋集中提问入口＋正文优先。可以提升精致度与辨识度，但不要恢复通用左侧导航＋右侧卡片的后台模板。

避免：大面积单调黑白、炫光／无意义渐变、过多阴影、装饰性统计、彩虹徽章、虚假进度条、巨型营销插画、玻璃拟态影响文字对比、为了整齐而隐藏证据限制。

## 5. 全局框架

顶部包含“案卷”品牌标识、“AI 产品调查与证据核查”定位及“发起调查”真实入口。可显示“本地工作区”，不虚构账户、通知或组织选择。

主内容有明确 H1；提供“跳到主要内容”。详情宽屏使用正文与窄阅读目录的关联布局，正文占主要空间；窄屏将目录移到正文前或其他不遮挡内容的位置。目录只做页面章节定位，不伪装调查列表。

## 6. 页面一：首页／发起调查

用户目标：明确产品与问题范围，完成一次调查提交。

由上到下：

1. 简洁产品定位与主标题，例如“关于这款产品，你想查清什么？”
2. 主提问区：可见标签、多行输入、简短问题范围提示、主要按钮“发起调查”。输入是第一视觉中心，不让介绍内容压过它。
3. 轻量阅读引导：提出问题→查看真实状态→沿引用复核。用文字与排版表达，不用虚构调查卡片填充。
4. 本地版本及服务限制提示，字号克制但保持可读。

输入需支持 1–4000 字符校验；可提示明确产品、版本／套餐及关心的能力。设计空输入、聚焦、已输入、校验错误、提交中、网络提交失败状态。错误贴近字段、保留输入；提交中禁止重复点击，按钮明确反馈。只有服务端接受后跳详情，不显示虚假成功。

示例问题如需使用，只作为输入提示，不表示已有结论或案例。不要增加热门问题、历史记录、数量指标。

## 7. 页面二：调查详情通用结构

顶部：当前完整问题＋状态标签＋服务端执行阶段＋阶段／状态更新时间。长问题自然换行。调查 ID、创建／开始／结束时间等次要信息可置于可展开执行信息区，不能遮盖主要状态。

操作区只出现适用操作：手动刷新、按后台权限重试、等待确认时的身份表单、发起新调查。区分“刷新状态”和“重新执行”，不使用含糊的统一“重试”覆盖所有错误。

### 详情状态变体

| 状态 | 用户应看到 | 操作与设计限制 |
| --- | --- | --- |
| PENDING 排队中 | 等待任务执行的说明、更新时间 | 可刷新；不编造队列名次、剩余时间 |
| RUNNING 调查进行中 | 已保存阶段、更新时间 | 只展示实际阶段，不自动亮起下一阶段，不画百分比 |
| AWAITING_CONFIRMATION 等待身份确认 | 明确原因、对象信息、确认表单 | 停止后台轮询，不暗示仍持续调查 |
| SUCCEEDED 调查完成 | 本轮对应快照的回答与证据 | 标注快照版本／生成时间；并非所有主张都一定成立 |
| FAILED 调查失败 | 真实错误代码、解释、重试权限理由 | 重试只按后端 allowed；失败不是没有讨论 |
| CANCELLED 已取消 | 明确已取消、更新时间 | 只展示状态，不添加尚未支持的取消按钮 |

可显示的执行阶段名称：任务已创建、解析产品身份、联网检索、获取来源原文、核查主张、整理回答、结果已保存。阶段文本由真实数据选择，阶段图不能编造成已完成进度。

### 身份确认表单

显示后台确认原因；字段按当前表单提供产品名称、官网、版本／套餐，以及依据来源链接、原文、实际获取时间和依据说明。清楚标注必需项与未知可留空项，不自动伪造依据。长原文采用多行输入。设计字段错误、提交中、提交失败、记录已变化的反馈。

409 冲突文案示例：“调查数据已变化，已刷新当前状态，请核对后再操作。”不能暗示原操作自动成功或自动再次执行。

### 网络与历史保护

网络断开时保留最后成功读取内容，显示“当前读取失败”和最后读取时间；自动恢复尝试耗尽后提供手动刷新。页面读取失败、操作失败和后台执行失败为三种不同错误，视觉上应区分。

当前失败但存在旧结果时，失败状态仍位于主信息区，旧结果标题明确标注“历史结果”，显示其版本及生成时间，不能贴本轮完成标签。快照读取失败显示读取错误，不画成空结果。

## 8. 调查结果：连续阅读的五个章节

### 8.1 调查回答

展示产品身份、版本／套餐（缺失为未知）、回答生成时间、保留段落和换行的长正文。引用编号内嵌正文，可点击定位对应证据或精确映射；设计目标高亮、键盘焦点与返回阅读位置的锚点。

引用与来源均属于当前快照。不要用装饰脚注替代真实引用，不根据句子相似度匹配来源。正文按纯文本安全呈现，不依赖插入 HTML 的设计。

### 8.2 主张核查

每条主张呈现：完整表述、内容性质、核查状态、核查理由、适用范围、关联证据及关系、尚存限制／冲突。

核查状态使用文字：尚未核查、材料支持、材料反驳、存在争议、证据不足。关联关系使用：支持、反驳、上下文、无关、无法判断。

“材料支持”不要设计成绝对真理认证。来源存在不代表支持主张；官方宣称须明确说明其属性。关联证据链接可跳来源，冲突／缺口链接可跳限制章节。

### 8.3 引用与来源原文

来源应支持逐条深入阅读，不仅是外链小卡片。每条尽可能显示：

- 来源标题、网站、作者、可换行 URL。
- 来源类型与内容性质、发布时间、获取时间、适用版本／套餐、原文语言。
- 读取状态：已取得原文、尚未获取、读取失败、访问受限、仅有搜索摘要。
- 原文摘录，译文独立分区；定位信息与上下文；读取失败时的真实说明。
- 来源独立性、判断理由、共用上游分组及上游链接（已有时）。
- 关联主张与准确引用关系。

来源类型：官方材料、社区材料、第三方材料、未知。内容性质：事实陈述、官方宣称、使用者报告、观点、未知。这两个维度不可混成一个“可信／不可信”分数。

独立性：独立来源、共用上游来源、未知。多个链接不能自动显示“多方独立证实”。原文未成功读取不展示伪造引语；摘要不标为原文；未知字段显示未知或明确缺失，不自动补全。

可用折叠组织次要元数据，但原文、限制与来源属性不能藏到普通用户难以发现。优先使用锚点和原有章节，避免强制依赖新的抽屉数据接口。

### 8.4 冲突和证据缺口

分别呈现尚未解决的冲突、已记录处理说明的冲突、证据不足主张、限定搜索范围内未找到、未取得原文、读取失败、身份不明确。

缺口有搜索范围时显示范围；没有冲突记录不等于不存在冲突，没有缺口记录不等于已经查全。此区应容易发现，不能放到视觉上几乎不可见的页脚免责声明中。

### 8.5 快照版本与生成信息

显示版本、生成时间、快照／调查标识及已有生成信息。日期采用上海时区并标注。历史结果有醒目标识；不生成未支持的版本切换控件。长 ID 不撑破布局。

## 9. 必须交付的模板场景

| 编号 | 画面 | 核心验收 |
| --- | --- | --- |
| S01 | 首页默认＋输入聚焦 | 主提问入口鲜明，定位清楚 |
| S02 | 首页校验／提交中／网络失败变体 | 反馈可见、输入保留、按钮状态清楚 |
| S03 | 详情排队中 | 无假进度、状态时间清楚 |
| S04 | 详情调查进行中 | 实际阶段突出，无虚构百分比 |
| S05 | 详情等待身份确认 | 原因和表单易理解 |
| S06 | 调查完成的完整阅读页 | 五章齐全，回答和原文关联清楚 |
| S07 | 长回答＋大量证据 | 长 URL、混合语言、目录与来源不溢出 |
| S08 | 失败允许重试／禁止重试两个变体 | 权限理由明确，错误不等于空结果 |
| S09 | 断网保留内容＋手动刷新 | 陈旧数据／读取错误／时间均可识别 |
| S10 | 当前失败＋历史快照 | 当前状态和历史属性不混淆 |
| S11 | 空回答／空主张／空证据／快照读取错误 | 各自不同文案，不统一称“没有结果” |
| S12 | 409 数据变化反馈＋已取消状态 | 不自动重放，不添加取消能力 |

这些为同一产品的页面状态变体，不生成十二套不同风格。每个场景都需标清使用条件。优先完成首页和成功阅读页，再扩展等待、确认与错误。

## 10. 响应式与可访问性

必须展示 1440、1024、768、390px 下的布局方案。宽屏正文与目录有关联但不挤压阅读；1100px 以下使用紧凑顶部框架，640px 以下单列、16px 页边距。顶部框架本身不要求桌面侧栏。

所有宽度无横向滚动、无文字遮挡、无悬浮控件盖住证据。长链接允许断行，正文保持舒适行长。重要触控目标至少 44×44px，引用有足够可点击面积；保留 hover、focus、active、disabled 状态。

键盘可完成输入、提交、刷新、确认、引用跳转；跳转目标有可见反馈。禁用按钮伴随说明，错误关联对应字段。动效仅辅助状态理解，支持减少动效；错误和限制不随动画消失。

## 11. Stitch 输出要求

1. 先给统一设计方向，再生成可对应现有功能的页面模板；标注各画面的场景编号。
2. 首页和成功详情提供完整桌面／平板／移动布局，其他状态至少给桌面和移动变体，四宽度规则明确。
3. 提供色彩、排版、间距、圆角、边框、控件状态、语义标签和证据来源组件规范，组件之间风格一致。
4. 成功页需要完整长页而非只有首屏；包括主张、原文、限制和快照信息。
5. 说明引用点击／目录定位／折叠信息的目标和响应，避免只有漂亮静态占位。
6. 可导出时输出语义化、组件化 HTML／CSS 或适配 React 的结构。实现环境是 Next.js＋CSS Modules；不要求添加后台或重新创建项目。
7. 设计内容与设计样例明显区分，不以生成图、假 URL 或演示文案作为真实证据。开发接入时以 src/contracts 和实际 HTTP 为准。

## 12. 可直接附给 Stitch 的开场指令

请为中文 AI 产品调查工具“案卷”生成一套精致、明亮、可信的前端模板。请完整遵守本需求文档，重点设计“集中提问的首页”和“正文优先、引用可追溯的调查详情长页”，并提供等待、身份确认、失败、断网、历史结果等同风格状态变体。采用顶部品牌栏，不使用通用左侧导航后台模板；以浅蓝灰背景、白色阅读面、深蓝文字与品牌蓝构建层级。界面要帮助普通用户读懂结论，并让严谨用户追溯原文、识别官方宣称、同源转述、冲突与缺口。不要添加文档未开放的功能，不要编造真实调查成功数据。请先完成 S01 与 S06 的完整响应式设计，再基于统一规范扩展其余场景。
