```text
本轮不新增自动补查、建议列表、导出、对外取消 API、历史切换或公开部署。Worker 既有内部取消/超时机制仍须正确维护。
```

# 板块一：不依赖甲的新代码或页面交付

这里的“不依赖甲”仅指可以由乙丙先行开发；数据库环境、真实核查者、独立复核者等可能仍是外部条件。**阶段 1、2 可与阶段 3 的摸底并行**，但最终工程验证需覆盖后续修改。

## 阶段 1｜工程环境、数据库、迁移与回归（E1）

**目标**：恢复专用测试环境，建立当前真实、可重复的工程基线。

**复制给 Codex：**

```text
执行乙丙阶段 1：建立可信的工程验证基线，完成 E1 范围内的专用测试库、迁移、回归和 CI 核实。

先从仓库实际内容入手：阅读 README、乙丙开发与验收方案、数据库和 Docker/PostgreSQL 配置、迁移目录、verify/测试脚本以及 CI 工作流；确认当前分支、HEAD、git status、测试库与其他环境的隔离方式。不要猜测数据库名、启动命令和测试命令。

在确认目标确实是专用测试库、不会破坏未知数据后，恢复连接，按 README 执行迁移和适用的工程验证。发现环境配置或工程回归问题时，定位根因并做最小修复，先跑相关测试，再跑规定的完整 verify。确认迁移可追踪、原调查功能未受到意外改变。

核实“当前提交”的托管 CI 真实执行情况；只有能够访问实际 CI 运行记录时才能报告通过。无法访问时提供需要人工核实的具体项，不得引用历史通过计数。仅在 README 的既有状态位置更新经核实的信息。

最终给我：实际使用的测试库身份与迁移版本、执行的命令及结果、verify 是否全过、CI 是已核实还是待核实、失败项与解决结果。不得因本地测试成功就声称 CI 已通过；若条件未满足，E1 保持未完成。
```

**阶段结束标准**：专用测试库可用、迁移和工程 verify 真实通过；托管 CI 结论有当前运行证据，或明确保留待核实。

## 阶段 2｜A/B/C 案例复查与 D1 评估工具补齐（E2、E4 准备）

**目标**：让三案材料和评估记录足以支撑后续真实对照；把“运行失败但没有快照”从记录缺口变成受支持的情况。**真实核查和独立复核仍需实际人员完成**。

**复制给 Codex：**

```text
执行乙丙阶段 2：整理 A/B/C 三案的可追溯材料，并修复 D1 评估/记录工具目前阻碍真实失败记录的问题。不要代替真人核查与复核。

先定位 A/B/C 案例文件、参考问题/答案、证据与来源、Q/C/E 对照规范、D1 状态与验收记录、现有只读评估器、记录 CLI 和测试。阅读每案实际内容后，查找引用、定位、原文与译文、时间、适用条件、同源支持、冲突及未知的真实问题；区分“根据已存证据可以修复的错误”和“需要真实核查者/独立复核者判断的事项”。保持材料原意和历史追踪，不把官方宣称当独立证实，也不把模型归纳当原句。

按项目已有记录方式修正可核实的错误，列出三案各自仍需真人确认的具体问题。问题与关闭条件只更新既有 D1 状态记录；证据、日期、署名、复核意见只能根据真实材料放回原位。没有真人实际完成审核，不得判 E2 全部完成。

同时检查 D1 CLI 是否仍强制调查 ID 与快照 ID 同时存在。若存在缺口，做最小向后兼容修改：实际执行失败且无快照时允许如实记录失败状态、已存在的实际标识、原因和证据；成功记录仍须有真实快照；NOT_RUN 只表示未执行。兼容旧记录格式，使用唯一 run-id，不覆盖既有 JSON。新增定向测试覆盖成功、有真实失败但无快照、未运行、非法输入及历史兼容；保持只读评估器不擅自篡改原材料。

执行相关测试后，按 A/B/C 分别汇报：已改材料、依据、待实际核查/独立复核问题；另给出 CLI 修改、测试结果与真实失败记录的操作方法。缺人工签署时标为等待真人，不得把工具完成说成 E2 验收完成。
```

**阶段结束标准**：三案可程序核查的问题已处理、真人核查清单明确，D1 能正确记录真实失败无快照；E2 只有拿到真实确认和独立复核后才能关闭。

## 阶段 3｜建议通路的数据模型、存储和 HTTP 契约（E3 前半）

**目标**：围绕一个能独立验证的目标——“创建可追踪的建议任务，并能安全存取及查询其状态/结果”——完成最小公共接口，而非拆成多个孤立技术小任务。

**复制给 Codex：**

```text
执行乙丙阶段 3：在不依赖甲真实生成能力的前提下，完成建议通路的数据、存储、请求/查询 API 与共享契约。阶段内请自行安排设计、实现和测试，但不要越界开发 Worker 真实生成或甲的页面。

先完整检查 README、乙丙方案、协作边界，以及现有 AdviceSchema、UserConditionsSchema、Advice 表、Job、Investigation、Snapshot、Answer、Repository、HTTP Schema/路由、迁移和测试。具体查证当前 Job 与 investigationId 的关联和唯一性限制，不能直接把一调查一 Job 当成可支持同快照多次建议。列出已有/缺失能力、最小数据关系和共享 API 的设计方案。

实现前先定义并显式说明最小语义：建议绑定不可变 snapshotId；支持同一快照不同真实用户条件的不同建议请求；同一幂等请求重复提交应得到同一逻辑任务或等价结果；建议不覆盖客观 Answer。创建请求、任务状态/结果查询、条件不足、失败、无权限、无效快照、相同幂等键但不同载荷等都应明确处理。避免在缺乏甲确认时擅自冻结与 Provider 紧耦合的字段；需甲确认的具体接口决策列为清单，但可以继续实现不会冲突的公共基础部分。

在现有设计上做最少必要且兼容的迁移和数据访问实现，包含 Advice 写前/读后校验、快照不存在/归属不符、无效或损坏结果、重复发布与并发唯一性处理。创建/查询 HTTP API 和甲可复用的共享 Schema；创建只返回真实可追踪任务，不得同步伪造生成成功。所有状态/结果仅取自真实持久化记录。保留原调查 API、Job 与客观 Answer 行为。

测试覆盖同快照不同条件、幂等重复/冲突、并发提交、无效和跨归属快照、存储读写校验、失败查询及原调查回归。允许使用仅限测试的 stub/mock 来验证边界，不得将测试结果写成真实建议。

最后汇报准确的数据表/迁移、路由/方法、Schema 和测试结果；列出还需与甲确认的契约点及 Worker 待接入接口。本阶段交付是公共基础，不代表 E3 整体完成。
```

**阶段结束标准**：持久化、任务创建、状态/结果 API 及共享 Schema 的规则可独立验证；数据迁移兼容、旧调查回归通过；待甲确认项明确。

## 阶段 4｜建议异步 Worker 生命周期与安全发布（E3 后半基础）

**目标**：在没有真实 Provider 时，先让建议任务的并发、失败、重试与发布安全具备可测试的工程闭环。**此阶段不能宣称真实 E3 已完成**。

**复制给 Codex：**

```text
执行乙丙阶段 4：接续上一阶段的持久化与 API，完成建议异步任务 Worker 的完整工程生命周期及故障测试；甲的真实 Provider 在后续阶段才接入。

先阅读仓库真实 Worker/队列实现、Job 领取、租约/心跳、超时截止、内部取消、有限重试、发布令牌、事务边界、原调查任务测试，以及阶段 3 的实际 API/数据模型。确认哪些机制可以复用，避免破坏既有调查 Worker。根据真实代码决定最小实现，不强制某种重构结构。

打通建议请求入队→Worker 领取→续租与截止检查→调用建议 Provider 注入点→校验返回→持有效令牌原子发布 Advice→终态与 HTTP 查询。真实 Provider 不可用或缺配置时必须呈现真实阻塞/失败，绝不能用模拟结果作为生产成功。正确区分“用户条件不足”和“系统执行失败”，并与待甲确认的 Provider 契约对齐；若生成语义无法确认，先实现安全接口/错误路径，标注未集成部分。

重点保护并发与失败边界：重复领取、过期令牌、超时后迟到结果、心跳中断、重复发布、有限重试耗尽、事务回滚、损坏结果、不可见/不属于请求方的快照。旧调查任务必须继续工作，现有内部取消机制不能被误删，也不要新增对外取消 API。

补充确定性的 Worker/Repository/API 集成测试，测试替身只用于触发竞态和错误；重跑原调查关键回归。必要时修复上一阶段的轻微契约缺陷，但先说明跨阶段修改原因，不扩大到生成语义或页面。

最终给出真实状态机及调用接入点、测试覆盖与结果、仍需甲确认/提供的 Provider 输入输出与配置。把无法进行真实生成的事项标为待甲，不宣布 E3 已通过端到端验收。
```

**阶段结束标准**：建议 Worker 和发布安全在测试环境有完整可验证的生命周期；生产真实生成仍待甲提供。

# 板块二：依赖甲的真实能力与前端

进入此板块时先核实甲已实际提供的代码、配置、契约及页面，不按计划完成时间推定其已就绪。**契约沟通可以在阶段 3 起就进行**，不必等到阶段 5 才对齐；阶段 5 的真实接入则确实依赖其能力可用。

## 阶段 5｜对接真实 Provider，完成首条正式端到端闭环（E3、E4 起步）

**目标**：先跑通“建议完整链路”和“一条真实客观调查”，避免直接用三案混合排错。可因甲的真实能力不足而部分阻塞，但不制造模拟通过。

**复制给 Codex：**

```text
执行乙丙阶段 5：与甲已提供的真实 Provider 和已确认的最小契约对接，先完成建议通路正式端到端，再选择一个边界明确的客观问题验证正式调查链路。开始前先检查甲当前实际交付状态，不要假设已完成。

首先读取协作边界、甲的真实调查/建议 Provider 及配置、阶段 3–4 已有实现、共享 HTTP Schema、正式 API/Worker、D1 CLI 和评估工具。核对与甲已明确确认的输入/输出、UserConditions、snapshotId、引用、条件不足、错误、超时、重试及取消/截止语义。若关键契约仍有冲突，给出可直接让甲确认的精确差异；避免擅改甲的生成算法或 F1–F6 页面。

在 Provider 确实可用时，以最小适配连通真实建议链路：真实快照+真实用户条件→创建请求→真实任务 ID→Worker 调用甲的 Provider→有效令牌原子发布→Advice 存取校验→HTTP 查询真实终态与结果。核验同请求幂等、同快照不同条件、无效令牌、超时/失败/条件不足、配置缺失和原调查回归。不能用 mock 证明真实端到端成功；缺少真实用户条件时不得编造。

随后只选仓库已有依据支持的一条范围明确的客观问题，通过正式 API 和真实 Worker/调查 Provider 运行，记录真实 investigationId、时间、终态及成功时的 snapshotId。成功时用现有只读评估器及唯一 run-id 做结构检查（不覆盖历史），把人工语义复核单独标注。实际发生失败且无快照时，使用阶段 2 的合法记录路径记为 FAILED；不能写作 NOT_RUN，也不能造快照。

乙丙只修公共 API、任务、存储、迁移与记录工具的问题。甲的生成、证据语义和页面问题输出复现条件交甲处理。把可供甲 F5 直接调用的路由、方法、共享 Schema、状态/错误协议和示例整理在本次回复中，不另建重复交接文档。

最后按“真实建议链路”和“单案真实调查链路”分别列出实际运行证据、测试与阻塞。只有真实建议链路和相应回归通过，E3 才可判完成；未接入的真实能力不得宣称已验证。
```

**阶段结束标准**：E3 有真实建议完整链路及并发/失败回归证据；至少一条客观问题能通过正式调查链路验证，或明确保留甲侧阻塞。

## 阶段 6｜三案正式 Q/C/E 对照与问题闭环（E4）

**目标**：真实系统结果进入既有 D1 案例对照，定位并修复乙丙负责的问题，为之后 E5–E7 的人工验收准备可靠依据。

**复制给 Codex：**

```text
执行乙丙阶段 6：以现有 A/B/C 案例材料为依据，对三案逐一进行正式调查 API/Worker 的真实运行和 Q/C/E 对照，同时验证同一实际产品在真实条件下的建议出口，完成乙丙范围内的缺陷闭环。

先读取 A/B/C 原始问题、证据和参考 Q/C/E、D1 案例规范及状态记录、只读评估器、D1 CLI、阶段 5 的真实运行方法、乙丙方案中的 D2 展示口径，以及甲已实际可用的调查/建议能力和页面。逐个案例核对输入与参考是否仍适用，切勿用旧运行结果/fixtures 冒充本轮正式执行。

对 A/B/C 分别通过正式 API/Worker 发起真实任务，保存实际时间、真实 ID、终态、成功时的快照和证据定位，失败时保留实际失败原因及无快照记录。每次成功评估使用唯一 run-id，沿用已有只读评估器，不覆盖旧 JSON。对照 Q/C/E 的结构结果之外，列出必须由真实人员完成的语义复核：事实/宣称/报告/归纳、原文/译文、同源/独立、冲突/未知/缺口等；没有人工核查就明确标待复核。

三案都是客观问题，不能单凭三案通过判断建议功能。另选真实使用者提供的同一产品建议问题与真实条件，使用已形成的客观快照发起真实建议；核对不同条件的任务/结果是否正确分开、条件不足是否被清楚呈现、客观答案是否仍被保留、来源能否追溯。若缺真实问题/条件则保留阻塞，不造数据。

若甲的相关前端已可用，可核对必要的状态、来源点击和客观/建议呈现是否与 API 真实结果一致；但不要接管 F1–F6。把公共层缺陷（乙丙）做最小修复并回归；把 Provider 内容、来源语义与页面缺陷形成可复现的问题交甲。更新状态时仅用仓库现有 D1 状态记录和实际证据原位，未发生的运行、人工复核、复验不能记为已完成。

最后给出每个案例的真实终态、Q/C/E 结构对照、人工复核待办、建议出口真实验证结果、修复与复验情况，以及 E4 剩余阻塞。按现有规范判断 E4 是否可关闭；不要顺便宣称 E5–E7 已完成。
```

## E5–E7：不另拆开发阶段，但仍必须实际完成

这三项是**使用真人进行验证并交付素材**，不适合让 Codex 按“阶段完成 = 验收完成”来操作。完成阶段 6 后按项目原方案直接组织：

| 验收活动 | 人来完成的核心动作 | Codex 何时介入 |
|---|---|---|
| **E5 / D2** 两种真实示例与三分钟理解验证 | 选真实客观卡、同一产品的真实建议卡；未参与开发的读者阅读三分钟后复述，确认原话/译文/归纳、宣称/事实、同源/独立、未知与状态；有误解则复验 | 只协助整理既有材料、核查记录完整性、排查属于乙丙公共层的缺陷；甲处理页面和生成问题 |
| **E6** 至少五名目标用户试用 | 真实用户实际使用系统；匿名记录原问题、时间、理解情况、卡点、责任人、修复及复验，不采集私人联系方式 | 根据真实反馈生成最小修复任务，修乙丙侧 API/Worker/存储问题，跑回归；不模拟用户 |
| **E7** 三份真实演示素材 | 真实查询分别覆盖客观、海外冲突、补充真实要求后的建议；每份有真实答案、一句话说明、实测可点击来源和实际截图/录屏；交核心成员 | 整理已存在的查询、证据和素材索引，发现功能缺陷时修乙丙侧问题；不杜撰画面或路径 |

如实际验收发现工程缺陷，可以把下列**通用修复提示词**交给 Codex，而不另建立第 7、8、9 个开发阶段：

```text

【粘贴真实问题原话/复现步骤/日志/相关文件或运行 ID】

先查阅 README、乙丙开发与验收方案、甲与乙丙协作边界、相关源码/测试和既有验收记录，判断问题属于公共 API/任务/Worker/存储/评估工具，还是甲负责的前端/Provider 生成与来源语义。若不属于乙丙职责，只提供精确复现、预期/实际差异及建议交甲的内容，不越界修改。

若属于乙丙，提出最小修复方案，修改代码并完成定向测试和相关回归；说明是否需要实际用户/读者再次复验。不要以自动测试代替真人复验，不编造任何用户反馈。按仓库既有位置更新经核实的真实状态，不新增重复总结文档。
```

**总验收条件仍以原方案为准**：E1–E7 全部关闭、D1 符合案例规范、D2 经真实读者验证通过、无阻断问题、甲的前端和真实生成可供实际使用。**六个 Codex 阶段全部执行完，不自动等于项目全部验收完成。**
