# 乙的真实服务接入方法

乙负责公共工程与 D1 人工核查材料，不承担甲的真实搜索或核查适配器。此文的“接入”指连接真实数据库和运行单元、维护公共接口，以及用真实材料完成独立验收。

## 环境接入

1. 安装 Node.js 24 与带 Compose 的 Docker，按 [README](../README.md) 执行 npm ci。
2. 保留现有 `.env`，只在没有文件时从 `.env.example` 复制。DATABASE_URL 指向业务库；TEST_DATABASE_URL 指向不同名称且以 _test 结尾的专用测试库。
3. 启动数据库、运行 db:migrate；另开终端分别启动 Web 与 Worker。Web 不替 Worker 执行搜索。
4. 使用首页提交实际问题，记录调查 ID 和真实执行错误。未配置提供方时失败是正确行为，不要手工改成 SUCCEEDED。
5. 运行 db:validate、verify、npm audit，保留 [公共工程验收记录与结论](公共工程验收记录与结论.md) 与 `.cache/acceptance/` 结果。

迁移只追加新文件，不改已经执行的迁移。不要用 db push 替代迁移，不对业务库执行测试的 TRUNCATE、DROP SCHEMA 或重置。需要新增索引／字段时同步 Prisma、SQL、Zod 与文档。

## 队列与持久化维护

- 创建真实异步调查必须使用 queue.enqueue 或 POST /api/investigations，避免先创建调查再独立入队留下孤儿记录。
- 用户确认、重试只走现有受状态保护的服务方法；不清空 failureCount，不重用失效 token。
- 最终发布只走 queue.complete。Repository 的低层方法用于受控存储和测试，不是绕过 Worker 的正式发布入口。
- 错误 JSONB、引用 ID、原句、版本链和关系列不一致必须拒绝，不“修正”成看似成功的结果。

## D1 真实案例

真实 D1 尚未录入，不能把测试夹具或 reference 中明确标假示例当作已完成案例。每个真实案例按历史规范保留六项：案例 ID 与产品版本／套餐；原始问题与意图；URL、原句、作者／站点／发布时间及获取时间；主张与证据关系及同源说明；冲突和范围明确的缺口；核查与独立复核记录。

先以独立 Markdown 交接给甲和丙，避免为了跑通 UI 把人工案例未经审查写成自动成功任务。若以后需要正式导入，应另行明确入口、来源标识与执行归属，仍须通过共享契约和事务发布，不直接插数据库绕过 Zod。

## 与队友衔接

甲交真实调用记录与原文，乙验证持久化／恢复并用 D1 对照，丙验证用户能区分原文、译文、归纳、失败和证据不足。新的提供方、字段含义、重试策略或来源独立性口径应三人共同确认后同步文档；不得单方面把缺配置失败替换成演示成功。
